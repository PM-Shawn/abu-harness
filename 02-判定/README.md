# 判定

看不懂的词查[常用词解释](../00-全景/常用词解释.md)。

判定这项制度管“一件事做完了没有、做对了没有”由谁说了算。Agent 最常见的缺陷是把“我改完了”当成“做完了”，把“测试看起来是绿的”当成“功能是对的”。阿布里的一次：2026-09-14 复核一批返工时，门禁命令写成了 `npm run verify | tail`，屏幕上显示退出码 0，可输出末尾是一串类型错误。命令链条停在了类型检查，测试一个都没有运行。

那条命令的 `| tail` 是在门禁后面接了一个只显示最后几行的小工具，屏幕上看到的成功是这个小工具自己的成功。另一件事是复审：阿布的一轮复审报告里有 17 条发现，逐条核验后 14 条是误报（82%）。这项制度只认机器能复现的证据，不认任何人或 Agent 的自述。

## 规则详解

### 做完了只认门禁退出码

**规则原文**

> “做完了”的标准是 `npm run verify` 退出码为 0。必须在本地亲自运行、亲自看退出码，不能把验证推给 CI，也不能相信任何 Agent 的自述。实现之后自己运行、测试、改到通过，没验证过不说“修好了”，不让用户替你测试。build 或 lint 不通过的代码不提交。
> 门禁命令名固定为三个：`verify:quick`（小步自检，lint + 类型检查 + 有改动的测试，30 秒内，不查覆盖率）、`verify:full`（lint + 类型检查 + 全量测试 + 覆盖率阈值）、`verify`（等于 `verify:full`）。所有仓库用同样的名字，自主循环的完成条件直接引用它们。
> 只认当前这一次运行的退出码和失败数为 0，不拿以前的通过数当依据。任何一个子套件是红的，就不能报告“门禁全绿”。

- **防的是什么**：Agent 改完代码就宣布完成，或者只跑了一部分测试就说“测试通过”。
- **阿布里的来历**：规范写明阿布的大量 bug 属于行为类，build 通过发现不了。阿布的三个仓库都有同名的 `verify` 命令，企业版后台的 PR 模板要求勾选“我已亲自运行 verify”。企业版部署验收也写明只认冒烟脚本（最简单的一次试运行）当前的退出码和“0 failed”，不以旧的通过数为准。
- **强度**：L2。脚本存在，任何一步失败整条命令退出码非零；但是否真的运行过、是否看了退出码，没有机器检查。CI 分步执行同样的检查，不直接调用 `verify`（见“CI 用汇总检查作为必需检查”）。
- **执行机制**：[`mechanisms/verify-scripts.jsonc`](mechanisms/verify-scripts.jsonc)（三个门禁命令的写法）；运行时用 [`mechanisms/run-gate.sh`](mechanisms/run-gate.sh) 取真实退出码。
- **怎样用到你的项目**：按 [INSTALL.md 第 3 步](../INSTALL.md#第-3-步-做完的标准)装好依赖和三个配置文件，把 `verify-scripts.jsonc` 里的脚本合并进 `package.json`，把 lint、类型检查和覆盖率换成你项目里的命令，然后把“`npm run verify` 退出码为 0 才算完成”这句话写进 AGENTS.md / CLAUDE.md。

### 门禁命令不接管道

**规则原文**

> 运行门禁命令时不接任何管道（例如 `| tail -20`）。shell 报告的是管道最后一个命令的退出码，`tail` 总是成功，门禁失败会被显示成成功。先把完整输出写进日志文件，再读日志：`npm run verify > 【日志路径】 2>&1; echo "REAL_EXIT=$?"`。
> 输出末尾不是测试和覆盖率的汇总时，说明命令链条中途断了，不管显示的退出码是多少，都判定为失败。

- **防的是什么**：失败的门禁被显示成成功，没运行过的测试被当成通过。
- **阿布里的来历**：2026-09-14 复核一批返工时，`verify` 输出末尾是一串 `tsc --noEmit` 的类型错误，却显示退出码 0。实际是链条停在类型检查，测试根本没运行。之后写进了 feedback 记忆，通宵任务书的硬性规则里也写了“取真实退出码，不接 `| tail`”。
- **强度**：L1。只写在记忆和任务书里，阿布没有脚本执行它。
- **执行机制**：[`mechanisms/run-gate.sh`](mechanisms/run-gate.sh)（模板仓库补充的脚本）：输出写进日志、报告真实退出码；设置 `EXPECTED_TAIL` 后，即使退出码为 0，日志里找不到汇总文字也判定失败。
- **怎样用到你的项目**：把脚本放进 `scripts/`，把日志目录加进 `.gitignore`，在规则里要求 Agent 用 `bash scripts/run-gate.sh verify` 运行门禁。

### 提交前自动检查

**规则原文**

> 每次 `git commit` 前自动对暂存的源码文件运行 lint（任何警告都算失败）和相关测试。不用 `--no-verify` 跳过钩子。钩子文件保持可执行，每个 worktree 都要有 husky 生成的目录，否则 git 不运行钩子也不提示；开发环境预检里检查钩子是否装好。

- **防的是什么**：带着 lint 错误或把相关测试弄红的代码进入提交历史；钩子被跳过或没装上时，提交前的检查等于不存在，而且没有任何提示。
- **阿布里的来历**：有一类工作目录里钩子没有安装成功，提交前的检查一次都没有运行，也没有任何提示，过了很久才发现；之后开发环境预检会在“钩子文件存在但没安装”时报错。另一次钩子被外部超时强行终止，提交前检查丢掉了一部分还没暂存的改动，钩子里的参数因此做了调整。
- **强度**：L2。`git commit --no-verify` 可以跳过，而且没有任何机制发现；钩子只看 `src/**/*.{ts,tsx}`，其他目录不检查；不运行 build 和类型检查。企业版后台的钩子里 ESLint 警告不阻止提交。
- **执行机制**：[`mechanisms/husky-pre-commit`](mechanisms/husky-pre-commit)，lint-staged 配置见 [`mechanisms/verify-scripts.jsonc`](mechanisms/verify-scripts.jsonc)。钩子里的 `--no-stash --no-hide-partially-staged` 两个参数就是为“被强行终止时不丢改动”加的，不能省。钩子安装检查的做法：`.husky/pre-commit` 存在而 `.husky/_/pre-commit` 不存在时报错退出，放进开发环境预检。
- **怎样用到你的项目**：`npm install --save-dev husky lint-staged`，再运行一次 `npx husky`（带包名的安装不运行 `prepare`），确认 `git config core.hooksPath` 输出 `.husky/_`；把钩子文件放到 `.husky/pre-commit` 并 `chmod +x .husky/pre-commit`，把 lint-staged 的文件范围改成你的源码目录。整个模板仓库只有这一份 pre-commit，其他机制的提交前检查都加在这个文件里。

### 生成物必须与源码一致

**规则原文**

> 仓库里提交了由脚本生成的文件（生成的数据表、打包产物、扩展包副本）时，每个生成脚本都要有 `--check` 模式：在内存里重新生成，与已提交的文件比较，不一致就失败，并打印重建命令。这些检查放进 `verify:full` 和 CI。E2E（让程序像真人一样打开应用、点击按钮的整条流程测试）开始前用当前源码重新构建被测的产物。

- **防的是什么**：改了源码却没重新生成，应用实际加载的是旧产物，测试和人看到的都是过期的东西。
- **阿布里的来历**：一次工具描述的修改没有进入浏览器运行时包，测试的人花了一晚上复现一个已经修好的问题；主进程没有自己的构建步骤，改了 TypeScript 不带打包结果就发出去的问题也出现过。于是有了模型数据、主进程读取器、浏览器产物三个新鲜度检查，以及 E2E 开始前的重建步骤。
- **强度**：L2。不运行就不检查；其中主进程读取器的检查只在 `verify:full` 里，CI 没有这一步。
- **执行机制**：暂无通用脚本，写法见 [`mechanisms/verify-scripts.jsonc`](mechanisms/verify-scripts.jsonc) 可选脚本里的 `gen:check` 一项。
- **怎样用到你的项目**：给每个生成脚本加 `--check` 参数（重新生成后逐字节比较，不写文件），再把它串进 `verify:full`。

### 结论要有实地证据

**规则原文**

> 回答“有没有”“对不对”“现状是怎样”这类问题时，首要目标是不误报。记忆、旧报告、会话摘要只作线索；其中提到的文件、函数、开关、版本号，先用读代码、grep、看 git 状态、在真机上操作核实过，再下结论。不迎合提问的人，找出很多问题不等于回答得好。

- **防的是什么**：Agent 凭过时的记忆或摘要回答，或者为了显得有用而报出一堆“可能有问题”。
- **阿布里的来历**：规范里未写明来历。相关的 feedback 记忆有一条：一个被压缩后续跑的会话照着摘要继续推进旧版本号的发版，实际那个版本已经跳号发布。
- **强度**：L1。只靠 Agent 读规则。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原文直接复制进 AGENTS.md。

### 自主循环的完成条件可以机器验证并且有上限

**规则原文**

> 让 Agent 自主循环（例如 Claude Code 的 `/goal`）时，完成条件必须可以度量、写清怎么验证，结尾带轮数或时间上限（`or stop after N turns`）。`/loop` 只用于轮询和等待。
> 循环里产出和验证分开：关键节点用 `/code-review` 或独立的会话复审。`/goal` 每轮结束时的轻量门控只读对话、不运行命令，不能当代码验收。
> 带界面的功能，完成条件再加两项：任务书顶部“待确认”一节已列全（可以为空）；每条 P1 用户故事的 Given-When-Then 都有对应并且通过的 E2E 测试。

- **防的是什么**：条件写得含糊，Agent 自己觉得“差不多了”就停；或者没有上限，一直循环下去；或者把只读对话的门控当成验收。
- **阿布里的来历**：规范里未写明来历。阿布的 `/goal` 模板把这三条写成了“铁律”。
- **强度**：L1。完成条件是否带上限，没有检查。
- **执行机制**：[`templates/goal-conditions.md`](templates/goal-conditions.md)。
- **怎样用到你的项目**：复制模板里的句子，把路径、命令和轮数换成你的。

### 改了逻辑就有对应层的测试

**规则原文**

> 改了逻辑就要有对应层的测试，测试层级由文件名决定：单元 `*.test.ts`、集成 `*.integration.test.ts`、契约测试 `*.contract.test.ts`、E2E `*.spec.ts`。改 API 路由要有集成测试，验证状态码、响应形状和鉴权是否接上。

- **防的是什么**：只改代码不补测试，或者测试写在不对的层级，门禁跑不到。
- **阿布里的来历**：规范里未写明来历。客户端的 PR 检查改动行覆盖率，是这条规则唯一的机器执行。
- **强度**：L2。客户端的 PR 要求改动行覆盖率不低于 80%，但可以用 label 豁免；企业版后台没有这项检查。
- **执行机制**：文件命名由测试框架的 `include` 配置识别；覆盖要求见“PR 新增代码的覆盖率不低于 80%”。
- **怎样用到你的项目**：在测试框架配置里按这四种文件名收集测试，把命名规则写进 TESTING.md。

### 跨端接口用契约测试锁定形状

**规则原文**

> 两端之间的接口（前端和原生层的命令、客户端和服务端的 API、公开仓和私有仓的 SDK）用契约测试锁定：命令名、参数名、请求和响应的形状。新增接口时在期望表里加一行；接口改名或删除时，测试在运行时发现并变红。两端共用的样本数据以一份为准，各仓的副本逐字节同步。

- **防的是什么**：界面这边把参数叫 A，后台那边已经改名叫 B，两边各自检查都通过，合在一起才出错。
- **阿布里的来历**：阿布保留的旧桌面壳（Tauri，后台用 Rust 写）的命令接口有一个契约测试，至今仍在默认门禁里运行：它实时解析 Rust 端注册的命令表，期望表里的命令必须还存在，因为 TypeScript 的类型检查看不到 Rust 那边用的参数名。私有仓的 SDK 契约测试借用公开仓的测试环境运行。
- **强度**：客户端 L3；跨仓 L2。客户端的契约测试在默认门禁内；跨仓 SDK 契约测试在私有仓 CI 运行，但私有仓没有分支保护。
- **执行机制**：暂无通用文件，把 `*.contract.test.ts` 放进默认测试即可。
- **怎样用到你的项目**：为每个跨端接口写一个期望表（名字 → 参数键），测试同时读取另一端的注册表做比对。

### 测试结果不随时间和随机数变化

**规则原文**

> 测试里不用真实的 `Date.now()`、无参 `new Date()`、`Math.random()`、`crypto.randomUUID()`、真实网络、真实定时器、真实文件系统作断言依据。时间用假时钟固定，随机数用固定种子或替身，网络用 mock 拦截。私有仓测试不含真实凭据，样本登录 token 用明显的假值。
> 单个测试体保持默认的短超时，卡住的测试尽快失败；准备工作给较长的 hook 超时。不全局调高测试超时。

- **防的是什么**：同一个测试这次过、下次不过，门禁的红绿失去意义。
- **阿布里的来历**：规范里未写明来历。测试配置里写明保留默认 5 秒测试超时，是为了让卡住的测试尽快失败，不被宽松的上限掩盖。
- **强度**：lint L3；其余 L1。客户端 `src/**/*.test.{ts,tsx}` 里的四种调用由 ESLint 直接报错；网络、定时器和文件系统的要求，以及其他目录和其他仓库，只靠规则。
- **执行机制**：[`mechanisms/eslint-test-determinism.mjs`](mechanisms/eslint-test-determinism.mjs)。
- **怎样用到你的项目**：把文件放到仓库根目录，把配置块加进 `eslint.config.mjs`（完整写法见 [INSTALL.md 第 3 步](../INSTALL.md#第-3-步-做完的标准)），`files` 改成你的测试文件范围。同一个文件命中多个配置块时，后面的 `no-restricted-syntax` 会整条替换前面的，所以这个配置块要放在靠后的位置。

### PR 新增代码的覆盖率不低于 80%

**规则原文**

> 每个 PR 新增或修改的代码行里，被测试执行到的比例不低于 80%，由 CI 用 diff-cover 对比 PR 的 base 分支检查。确实无法测试时，加豁免 label，并在 PR 正文“门禁”一节写明豁免理由；有豁免 label 并且正文写了豁免理由时，CI 放行，并在摘要里写明这次被豁免。

- **防的是什么**：整体覆盖率阈值只防下跌，新写的代码可以完全没有测试。
- **阿布里的来历**：规范里未写明来历。阿布用自己写的脚本对比 PR 的 base，结果写进 CI 摘要。
- **强度**：L2。在必需检查 `check` 里，但可以用 label 豁免；本地 `verify` 不包含它。
- **执行机制**：[05-进化 的 ci-diff-cover.yml](../05-进化/mechanisms/coverage/ci-diff-cover.yml)（vitest 生成 Cobertura 覆盖率报告，第三方工具 diff-cover 对比 PR 的 base 分支，阈值 `--fail-under=80`；这份 workflow 只判断豁免 label，豁免理由由审阅的人读，阿布自己的脚本会同时读取 label 和正文里的豁免理由），vitest 的 reporter 设置见 [05-进化 的 vitest.coverage-thresholds.ts](../05-进化/mechanisms/coverage/vitest.coverage-thresholds.ts)。PR 模板里对应的“豁免理由”一行见 [01-方向 的 PR 模板](../01-方向/templates/pull_request_template.md)。
- **怎样用到你的项目**：vitest 的 `coverage.reporter` 加上 `'cobertura'`，CI 的测试 job 取完整历史（`fetch-depth: 0`），复制 workflow，按文件开头的注释改集成分支名、豁免 label 和 diff-cover 版本；把这个 job 登记为分支保护的必需检查。本地想先看结果时运行 `pip install diff-cover` 后执行 `diff-cover coverage/cobertura-coverage.xml --compare-branch=origin/【集成分支】 --fail-under=80`。整体覆盖率阈值的规则见 [03-边界：覆盖率阈值只升不降](../03-边界/README.md#覆盖率阈值只升不降)。

### 被验收的功能运行真实实现

**规则原文**

> 不用假实现骗过验收，不为了通过测试写绕行代码。mock（测试里代替真实网络、真实时间的假部件）只用于隔离网络、时钟、文件系统、第三方服务；被验收的功能本身必须运行真实实现。检查“某个值有没有送到审批或授权那一步”的测试，必须从真实的工具入口出发；直接调用审批之后那段程序不算覆盖。

- **防的是什么**：测试只检查了“审批通过以后”那段程序，从用户点击按钮到发起审批之间的那一段没有任何测试走过；每个测试都通过，用户点击按钮却没有反应。
- **阿布里的来历**：阿布出现过三次同类问题：测试都绑在回调函数或纯函数那一层，从真实入口到审批那一步之间的一段没人走过（2026-09-05 的一条复审发现 F1 是其中之一）。之后在 TESTING.md 加了“这类测试必须从真实入口出发”。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原文复制进 TESTING.md；复审时专门检查这类测试的入口。

### 行为类改动在真机上走一遍

**规则原文**

> 行为类改动必须真机验收：桌面应用在真实的应用窗口里走一遍受影响的用户路径，服务端真实调用接口。build 和单测通过不等于功能正确。改打包、签名、更新、权限、Windows 行为时，在对应的真实平台上运行验证。新 worktree 先运行初始化和环境预检，再开始开发。
> 验收证据（日志、截图、机器可读的结果）放进仓库里的证据目录，写明哪些还没验证，不宣称没验证过的项目已通过。

- **防的是什么**：“测试全绿”但用户一点就出错。
- **阿布里的来历**：阿布规范写明大量 bug 属于行为类（批量整理、草稿不显示、中文文件名文档），build 发现不了。部署时也遇到过：登录后闪回登录页，接口全部返回 200，只有用真浏览器点一次才能发现。
- **强度**：L1。PR 模板有勾选项，没有检查；外部验收脚本和真实应用冒烟脚本存在，需要手动运行。
- **执行机制**：[`templates/acceptance-checklist.md`](templates/acceptance-checklist.md)（一个功能或一个 PR 的真机验收清单，单独成文件）、[`templates/evidence-README.md`](templates/evidence-README.md)。夜间交付说明里的“真机验收清单”一节是同一种清单放在交付说明内，见 [04-记录](../04-记录/README.md#交付说明必须有固定小节)。
- **怎样用到你的项目**：为你的应用写一个“启动真实应用、走一条路径，再从外部进程确认资源都已释放”的脚本；交付时附验收清单和证据目录。

### 判断界面状态读 DOM，截图只作证据

**规则原文**

> 定位界面元素、判断界面状态，一律使用 DOM 或无障碍树里的文本信息（程序内部对界面的文字描述，写着每个按钮叫什么、在什么状态）。截图只用作交给人确认界面的证据。

- **防的是什么**：模型看截图时认错位置、读错文字，做出错误判断。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原文复制进 AGENTS.md / CLAUDE.md；E2E 用按文字和角色定位的写法。

### 界面改动先给人看，再运行全量门禁

**规则原文**

> 界面部分完成后，先给用户看：每条用户故事附一组真实应用的截图，按业务流程的步骤排列，旁边标出界面用词。用户看过、确认不再修改后，再运行全量门禁、开 PR。

- **防的是什么**：界面往往要改一两轮，先跑完整测试再改等于测两遍；也防止没给人看过的界面直接合入。
- **阿布里的来历**：2026-09-13 作者定下这个顺序，写进了 feedback 记忆，之后进了工作区规范。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原文复制进 AGENTS.md 的开发流程一节。纯逻辑、无界面的改动照常先写测试。

### CI 用汇总检查作为必需检查

**规则原文**

> CI 的门禁分成几个并行 job（lint、类型检查、测试与覆盖率、构建），由一个汇总 job `check` 检查它们全部成功。分支保护登记 `check`，E2E 分片运行时再登记 E2E 的汇总检查，并打开“管理员也不能绕过”。汇总 job 必须写 `if: always()`。不在 `check` 里的 job 只作参考，红了也不拦合并，不能当门禁看。
> 没有分支保护的仓库，CI 结果只是参考；要当门禁，必须登记为必需检查。

**模板仓库建议**：把安全边界测试也作为一个 job 汇入 `check`。阿布还没有这样做，见文末缺口。

- **防的是什么**：几项检查里有一项失败，负责汇总的那一项就没有运行；GitHub 把“没有运行”当成“没有问题”，有毛病的代码照样合并进去。另一种情况是新加了一项检查却忘记登记，它失败了也没人拦截。
- **阿布里的来历**：阿布客户端的 `dev` 和 `main` 都登记了 `check`，并开启了“管理员也不能绕过”。没有分支保护的仓库，CI 全部只是参考。客户端 Windows 单测、依赖漏洞扫描、浏览器 E2E 目前都在 `check` 之外。
- **强度**：L3。`check` 是分支保护登记的必需检查。
- **执行机制**：[`mechanisms/ci-gate.yml`](mechanisms/ci-gate.yml)（汇总结构；上面建议的安全边界测试 job 以注释形式附在文件里，启用办法写在文件开头）；[`mechanisms/ci-gate.test.mjs`](mechanisms/ci-gate.test.mjs)（锁定结构的测试：删掉 `if: always()`、给门禁 job 加 `continue-on-error`、新增 job 不汇入 `check`，都会让它变红）。
- **怎样用到你的项目**：复制 workflow，换成你的命令；在仓库设置里把 `check` 登记为必需检查；把结构测试放进 `scripts/`，`test:infra` 会运行 `scripts/` 下全部 `*.test.mjs`。往 `check` 里增减 job 时，`needs`、`RESULTS` 和结构测试的 `GATE_JOBS` 三处一起改。步骤见 [INSTALL.md 第 4 步](../INSTALL.md#第-4-步-ci-与发版预检)。

### E2E 按改动范围分档运行

**规则原文**

> 真实应用的 E2E 全量交给 CI，并且是集成分支的必需检查。本地按改动范围选择：只改纯逻辑、文档、单测能覆盖的部分，本地不跑 E2E；改了某个功能的界面，跑冒烟 spec 加该功能的 spec；改了主进程、全局组件、E2E 公共辅助代码，或者改了界面文案（spec 靠文案定位元素），PR 必须等 CI 的 E2E 检查变绿。E2E 是 verify 之外的一道门禁，单独运行。

- **防的是什么**：每轮都本地全量跑，机器被占满、互相干扰出误报；或者改了全局的东西却没跑全量。
- **阿布里的来历**：2026-09-06 作者看到机器被多路门禁占满后定下分档，并把 `e2e-electron` 设为 `dev` 的必需检查（依据对六家 E2E 门禁做法的调研）。改浏览器授权链路任何一层时，还要本地运行一次对应 spec。
- **强度**：CI L3；本地分档 L1。`dev` 的必需检查包含 E2E 汇总检查；本地分档本身没有检查。
- **执行机制**：[`mechanisms/e2e-gate.yml`](mechanisms/e2e-gate.yml)（分片运行 + 汇总检查）。
- **怎样用到你的项目**：按你的项目列一张“改了什么 → 本地跑什么”的表，写进 TESTING.md；汇总检查名登记进分支保护。

### 改了 PR 的目标分支要重新触发检查

**规则原文**

> 修改 PR 的 base 分支不会触发 CI（workflow 只监听 opened、synchronize、reopened）。改了 base 之后，必须再推送一个提交，或者关闭再重新打开 PR，让必需检查重新运行。

- **防的是什么**：必需检查停在旧 base 的结果上，合并时看到的绿色不代表新 base 下的情况。
- **阿布里的来历**：2026-09-06 叠放 PR 合并出错之后定下。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原文复制进 AGENTS.md 的合并纪律一节；也可以在 workflow 的 `pull_request.types` 里加上 `edited`。

### 安全敏感改动要独立复审

**规则原文**

> 涉及登录、登录 token（登录后服务器发给你的通行凭据）、license、权限、文件删除、shell 调用、密钥的改动，由另一个独立会话或 `/code-review` 复审，不能只信实现它的会话的自评。PR 描述里勾选三项声明（亲自运行过门禁；查过鉴权、权限范围、审计、密钥不回显；写明迁移、兼容、回退），并由作者以外的人批准当前最新提交。

- **防的是什么**：实现的会话对自己的代码有盲区，安全问题只有换一个视角才能看到。
- **阿布里的来历**：规范里未写明来历。企业版后台有一个检查 PR 正文三项声明、要求非作者批准当前提交的 workflow。
- **强度**：客户端 L1；企业版后台 L2。客户端的 PR 模板里有一栏复审链接，没有检查；企业版后台的检查会变红，但仓库没有分支保护，红了也能合并。
- **执行机制**：PR 模板见 [01-方向](../01-方向/README.md#pr-按模板逐项填写)。
- **怎样用到你的项目**：把审批检查写成 workflow，并登记为必需检查；或者按路径识别安全敏感改动，要求 PR 附复审链接。

### 面向用户的新功能发版前做对抗式审查

**规则原文**

> 面向用户的行为类新功能，发版前做一次对抗式审查：由独立会话或多个 Agent 站在恶意用户和怪异数据的角度专门找 bug，包括超大输入、时区和时间戳异常、边界数据、并发与中断。审查产出多、误报多，每条发现都要先证伪再动手。

- **防的是什么**：只按正常用法测过，遇到极端输入就出错。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则；发现的处理用 [`templates/review-verdict.md`](templates/review-verdict.md)。
- **怎样用到你的项目**：原文复制进 AGENTS.md。定期的全项目审查见 [05-进化](../05-进化/README.md)。

### 复审发现先证伪再动手

**规则原文**

> 复审报告（来自子代理、静态分析、其他模型或人）都有误报。动手修任何一条发现之前，按四步核验：读发现引用的 `file:line` 的实际代码；证明失败会发生（复现、写针对性测试，或找出能打破它的输入）；查已有的防御；站不住的发现补一条回归测试写明原因，防止下次复审再报。子代理说的、别家产品的做法、文档写的，都只算待验证的假设。

- **防的是什么**：照着误报去“修”一个不存在的问题，引入新的回归。
- **阿布里的来历**：阿布的一轮复审里 17 条发现有 14 条是误报（82%）。常见误报：把单线程 JavaScript 当成多线程竞争、忽略已有的防御、忽略注释里写明的有意取舍、把一种语言的特性安到另一种语言上，还有“某模块没有测试”这类未经核实的整体判断。
- **强度**：L1。
- **执行机制**：[`templates/review-verdict.md`](templates/review-verdict.md)（逐条核验表）。
- **怎样用到你的项目**：原文复制进 AGENTS.md；每次处理复审报告时填一张核验表。

### 设计每两步由用户确认一次

**规则原文**

> 开发前的设计分步完成：第 1 步用户故事、第 2 步业务流程交用户确认后，才做第 3 步概念对照表、第 4 步功能清单；第 3、4 步交用户确认后，才进入技术方案。自主循环里，用户还没确认第 1、2 步时，目标只能写“起草第 1–4 步的产物”，不能写实现。循环里起草的第 3、4 步交给一个独立会话复审，复审通过才开始实现。

- **防的是什么**：Agent 按自己理解的需求直接做完，做出来的东西用户不要。
- **阿布里的来历**：规范里未写明来历。这几步的具体做法见 [01-方向](../01-方向/README.md)。
- **强度**：L1。没有记录“用户已确认”的位置，也没有检查。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：在任务书里给第 2 步和第 4 步后面各留一行“用户确认：【日期、原话】”，没填就不往下做。[需求任务书模板](../01-方向/templates/product-brief.md)的第 2 节和第 4 节末尾已经留了这两行。

### 界面上的每个元素都能追溯到流程

### 发版预检

**规则原文**

> 发版前运行一个预检命令，任何一项不对就退出码 1 并列出全部问题：各处版本号一致且与 tag 一致；更新日志有本版本的一节；（本地运行时）GitHub 分支保护的必需检查与仓库里登记的期望文件一致。同一个预检作为发版 workflow 的第一个 job，失败则整个发版变红。
> 发版前集成分支的 CI 全绿；在候选提交上打 RC tag，等多平台构建、签名、安装冒烟全部通过，再打正式 tag。

**模板仓库建议**：预检再加一项“正式版 tag 指向的提交已经在发版分支上”。阿布还没有这一项，见文末缺口；本目录的 `release-preflight.mjs` 和 `release-tag-commit.mjs` 已包含它。

- **防的是什么**：版本号不一致、更新日志缺失的版本被发出去；在一个没经过集成门禁的提交上打了正式 tag，也会完整发布。
- **阿布里的来历**：阿布规范写明版本号要在五个文件里同步，忘改锁文件会让无关改动混进别人的 PR。反例是 v0.13.5 的更新说明只写了一句“See the assets below”。盘点时发现：仓库没有 tag 保护规则，发版 workflow 不检查 tag 所在的提交，任何有写权限的人在任意提交上推送版本号匹配的 tag，就会发布到全部更新服务器。
- **强度**：CI L3；本地 L2。CI 里的预检失败，后续 job 不运行；本地运行和分支保护核对不运行就不检查；RC 是否打过、正式 tag 与 RC 是否同一提交没有检查。作者已决定不加 tag 保护规则，也不检查正式 tag 与 RC 是否同一提交。
- **执行机制**：[`mechanisms/release-preflight.mjs`](mechanisms/release-preflight.mjs)、[`mechanisms/release-tag-commit.mjs`](mechanisms/release-tag-commit.mjs) 及其测试 [`mechanisms/release-tag-commit.test.mjs`](mechanisms/release-tag-commit.test.mjs)、[`mechanisms/check-branch-protection.mjs`](mechanisms/check-branch-protection.mjs)、[`mechanisms/branch-protection.expected.json`](mechanisms/branch-protection.expected.json)（JSON 不能写注释：键是分支名，值是该分支必须登记的必需检查名，改成你的）。
- **怎样用到你的项目**：四个脚本放进 `scripts/`，期望文件放到 `.github/branch-protection.expected.json`，安装读取更新日志用的 Markdown 解析库（`npm install --save-dev mdast-util-from-markdown@^2 mdast-util-to-string@^4`），改掉版本号来源、更新日志文件名和发版分支名；推送 tag 前本地运行 `npm run release:check -- --tag vX.Y.Z --repo <owner>/<repo>`（本机要有已登录的 `gh`）。发版 workflow 里的预检 job 要先 `npm ci` 再运行预检脚本。

### 发版后核对

**规则原文**

> 发版后逐项核对：集成分支和发版分支没有互相缺失的提交（`git rev-list --left-right --count origin/dev...origin/main` 为 `0 0`）；Release 附件齐全；各更新服务器指向新版本，更新文件返回 HTTP 200；在真机上冒烟（尤其是 Windows 和没有安装开发环境的机器）；观察 24 小时的迁移、启动、更新报告，有后续就更新或新增一条记忆。

- **防的是什么**：发布流程显示成功，用户那边却下载失败或拿到旧版本；发版暴露的问题没人记下，下次发版再犯。
- **阿布里的来历**：规范里未写明来历。
- **强度**：两分支互不缺提交 L3；清单 L2；其余 L1。两个分支互不缺提交这一项由发版分支的必需检查保证；发版清单里对应的人工步骤由人照做，没有 workflow 自动核对；其余各项只是规范里的要求。
- **执行机制**：暂无脚本，只靠发版清单（[01-方向 的 release-checklist.md](../01-方向/templates/release-checklist.md)）。
- **怎样用到你的项目**：把核对项写成一个脚本，发版 workflow 的最后一步调用它；能自动的（HTTP 200 检查）先做。

### 发版流水线任何一步失败都不发布（可选）

适用于把桌面安装包发布到自己托管的更新服务器的项目，以及自动部署官网的项目。

**规则原文**

> 发版是一条自动流程：预检 → 各平台构建、签名、冒烟 → 上传并逐字节比对 → 更新线上的“最新版本是哪个”文件 → 公开 Release。后面的步骤依赖前面的步骤，任何一步失败都不发布。写“最新版本”文件的一段做成要么全部完成、要么全部恢复原样的一组步骤；线上版本比候选版本新时拒绝写入。静态网站部署也先测试，测试失败就不同步。

- **防的是什么**：部分平台构建失败时仍然发布，或者“最新版本”文件写了一半，用户拿到不一致的版本。
- **阿布里的来历**：阿布的发版 workflow 写明“部分平台构建失败不会发布”；先传不可变文件，全部回读后才改“最新版本”文件；排队中的旧 tag 不能覆盖新的。
- **强度**：L3。同一条自动流程里用 `needs` 串起，失败就不进入下一步。全部成功之后没有自动回退，发现坏版本只能再发一个更高的版本。
- **执行机制**：[`mechanisms/release-preflight-job.yml`](mechanisms/release-preflight-job.yml)（预检作为第一个 job，其余 job `needs: preflight`）。
- **怎样用到你的项目**：把你的构建、上传步骤接在预检之后；写线上文件的步骤先备份旧内容，失败时用 shell 的 `trap` 还原。

### 桌面应用自动更新的判定（可选）

**规则原文**

> 适用于带自动更新的桌面应用。更新检查返回三种结果：有新版本、已是最新、更新器未启用，不能把“未启用”显示成“已是最新”。下载的更新包校验 sha512，不符就拒绝安装。

- **防的是什么**：更新器被静默关闭，用户一直看到“已是最新版本”；下载损坏或被篡改的安装包。
- **阿布里的来历**：v0.41.0 发版后（2026-08-22）出过事故：非官方的 Windows 包更新器被静默关闭，界面却显示“已是最新版本”。
- **强度**：L3。由应用代码逻辑执行。
- **执行机制**：应用代码，暂无通用文件。
- **怎样用到你的项目**：更新检查的返回值用三种状态的联合类型，界面按三种状态分别显示。

### 服务端部署前后的核对（可选）

**规则原文**

> 适用于自己部署服务端的项目。部署前核实要部署的版本是线上版本的后代；部署后做健康检查和公网冒烟，登录这类流程用真浏览器点一次，清掉冒烟数据。保留数据的数据库升级先备份、停应用、确认结构，再执行。

**模板仓库建议**：部署前再核对这一版本的测试已通过，并且构建所用的提交就是要部署的提交。阿布这一项的修改方案已定，代码尚未修改。

- **防的是什么**：部署的起点和线上实际运行的版本对不上，要么已经上线的修复被覆盖，要么一批没上过线的提交跟着上去；接口全部正常，页面却用不了。
- **阿布里的来历**：2026-08-25 运营后台部署时，没有核对线上实际运行的版本，一批从来没有上过线的提交跟着上去了，Web 界面全部报 500 约一小时。另一次登录后闪回登录页，接口全部返回 200，只有真浏览器能发现。
- **强度**：L2。部署脚本自带线上版本核实和冒烟检查，但脚本可以不用；健康检查失败只提示人工回退，没有自动回退。
- **执行机制**：部署脚本，暂无通用文件。
- **怎样用到你的项目**：部署脚本第一步读取线上版本的提交号，用 `git merge-base --is-ancestor 【线上提交】 【待部署提交】` 核实，不是后代就终止；最后一步运行冒烟检查。

## 阿布专属规则示例

| 规则 | 为什么阿布需要它 |
|---|---|
| 新增插件 manifest 字段时在规格文档写明最低应用版本，用到新字段的包声明最低版本 | 阿布有官方插件市场，市场校验会拒绝要求比当前应用版本更新的包，市场里的每个包都要过安装器的同一套校验 |
| 运营埋点每个自然日至少发一次，设备 ID 在桌面端存进应用数据目录 | 运营后台规范把这两条记为已知的两个问题 |
| 旧壳命令与新壳处理函数逐一对应检查 | 阿布从 Tauri 迁到 Electron，新壳把不认识的命令变成无害的空实现，功能缺口会静默成功 |
| Electron 宿主界面测试进 verify | 阿布有 31 个 Electron 宿主测试文件，用 `node --test` 单独运行，运行前要先构建浏览器扩展 |
| 企业模块测试单独运行 | 企业测试依赖私有仓，公开仓的默认门禁不能要求有私有仓 |
| 企业版后台登录验收前运行只读预检 | 验收需要的环境变量和部署结构较多，先只读检查再开始验收 |

## 还没补上的缺口

| 问题 | 后果 | 打算补的机制 |
|---|---|---|
| “verify 为 0 才算完”在本地没有强制：没有 pre-push 钩子，提交钩子不运行 build 和类型检查，`--no-verify` 被使用时没有任何机制发现 | 提交可以带着 build 或类型错误 | pre-push 钩子运行 `verify:quick` 或类型检查 |
| 正式 tag 可以打在任意提交上：发版 workflow 不检查 tag 所在的提交，仓库也没有 tag 保护规则 | 没经过集成门禁的代码会被完整发布，且发布后只能再发更高的版本 | 预检里检查 tag 所在提交是否在发版分支上（阿布的 PR #600 已开，尚未合入） |
| 安全边界测试不在 PR 必需检查里，只在手动触发或发版时的构建里运行 | 安全边界的回归可以合入集成分支，到发版才发现 | 把它加进 `check`（阿布的 PR #602 已开，尚未合入）；是否再加进 `verify:full` 待定 |
| 测试确定性只执行了一小部分：lint 只管四种调用、只管一个目录；真实网络、真实定时器、真实文件系统没有检查；其他仓库没有对应规则 | 依赖真实时间和网络的测试进入门禁，随机变红 | 扩大 lint 范围，在测试 setup 里拦截全局 `fetch` |
| 改动行覆盖率只在一个仓库、只在 PR CI，不在 `verify:full`，其他仓库没有 | 其他仓库的新代码可以没有测试 | 各仓都加改动行覆盖率检查 |
| 安全敏感改动的独立复审没有检查：只有 PR 模板里的一栏链接；有审批检查的仓库没有分支保护 | 只有实现会话自评就能合入 | 按路径识别安全敏感改动，要求复审链接或非作者批准，并登记为必需检查 |
| 没有记录“用户已确认设计”的位置：设计确认门、任务书格式都没有机器检查，已有任务书出现了前四节顺序不对的情况 | 设计没确认就开始实现，事后查不出 | 任务书模板加用户确认记录，用脚本检查前四节标题 |
| 真机验收没有记录和核对：PR 模板的真机验收一栏没有任何 workflow 校验 | 行为类改动可以只凭单测通过就声称完成 | 模板写明走过的路径和运行过的 spec，CI 校验必填项 |
| 没有分支保护的仓库，CI 全部只是参考 | 检查失败了也能合并或直接推送 | 开启分支保护 |
| 私有仓的完整门禁不在 CI：CI 只运行一部分测试，没有类型检查和 lint 脚本；测试时使用的公开仓版本固定在一个旧提交上 | 私有模块的错误要到出包时才发现 | 补齐私有仓 CI 的门禁步骤 |
| 只作参考的检查长期不转为必需：Windows 单测、依赖漏洞扫描、浏览器 E2E 红了也能合并；分支保护是否被改动只在发版人本地核对 | 这些检查发现的问题照样合入 | 逐项评估后加入 `check`，用有权限的 token 定时核对分支保护 |
| 发布后核对和部署后回退只在文档里：更新服务器上的版本、下载文件是否可用、24 小时观察都没有 workflow；服务端部署健康检查失败后没有自动回退；运营后台推送不运行任何测试，部署脚本也不核对构建所用的提交是否就是要部署的提交 | 更新服务器出了问题要等用户发现；坏版本上线只能靠人恢复 | 发布后自动核对脚本；部署脚本记录旧镜像、失败自动切回，并核对构建提交与测试结果 |
| 文档里写的门禁与实际不一致：测试文档对必需检查、汇总 job、漏洞扫描方式、verify 包含哪些步骤的描述与实际配置不符 | Agent 把文档当事实，按错误的门禁情况行事 | 像测试清单一样，用脚本从配置生成门禁说明 |
| 各仓库门禁严格度不一致：lint 警告是否算失败、覆盖率阈值、测试超时、类型检查是否包含测试文件，各仓不同 | 同一条规则在不同仓库执行结果不同，搬代码或复用经验时容易误判 | 统一前需要作者决定 |

# 边界

看不懂的词查[常用词解释](../00-全景/常用词解释.md)。

Agent 做事很快，很少停下来想“这一步能不能撤回”：顺手用 git 把文件恢复原样，把私有代码提交到公开仓，在没有保护的分支上开自动合并。这些操作一步完成、事后难以补救，测试也发现不了。阿布 2026-09-25 的一件事：主会话给调研子代理写了“禁止用 git 回滚”，子代理又派出一个孙代理，孙代理用 `git checkout -- .gitignore` 撤销了自己刚加的一行。

假如当时工作区里有作者没提交的修改，同一条命令会把它们一起清除，而且找不回来。之后作者加了 Claude Code 的 PreToolUse hook（挂在 Agent 执行命令之前自动运行的小程序，见 [mechanisms/claude-code-guard/](mechanisms/claude-code-guard/)），并规定派子代理时要写明“你再派的子代理也照抄本节”（见 [templates/subagent-hard-rules.md](templates/subagent-hard-rules.md)）。规则按八组排列：git 操作、代码写法、保密、分支与合并、部署、测试环境、Agent 权限、作者的个人习惯。

## git 操作

### 不用 git 回滚

**规则原文**

> 禁止用 git 回滚代码：不用 `git reset`、`git restore`、`git revert`、`git clean`、`git stash`、`git checkout -- 【文件】`、`git checkout .` 之类的命令丢弃改动。用户说“回滚”时，指的是用文件编辑工具把代码手动改回上一个状态。

- **防的是什么**：工作区里常常同时有用户自己的改动、其他会话的改动和 Agent 的改动。Agent 一条 git 命令就能把别人没提交的工作一起丢掉，而且找不回来。
- **阿布里的来历**：规范里未写明来历。2026-09-25 发生过一次孙代理用 `git checkout -- .gitignore` 撤销自己改动的事（见本页开头）。
- **强度**：装了钩子的 Claude Code L2；其他工具 L1。2026-09-30 起，Claude Code 侧由 PreToolUse hook 在命令执行前拦截上面这些写法，hook 以退出码 2 拒绝并告诉 Agent 改用编辑工具。hook 只在装了它的机器上生效；Codex 不受它约束；把 git 命令藏进一个脚本再运行，hook 也看不出来。还有一种写法 hook 拦不住：不带 `--` 的 `git checkout 【文件】`（以及 `git checkout 【提交】 【文件】`）。从命令文本上看，它和切换分支的 `git checkout 【分支】` 分不清，hook 不去猜，这一种只靠本条规则约束。配套的做法是要求 Agent 切换分支一律用 `git switch`，`git checkout` 后面跟文件路径的写法一律不用。
- **执行机制**：[mechanisms/claude-code-guard/guard.py](mechanisms/claude-code-guard/guard.py)、测试 [guard_test.py](mechanisms/claude-code-guard/guard_test.py)、配置片段 [settings.snippet.json](mechanisms/claude-code-guard/settings.snippet.json)。把 `guard.py` 放到 `~/.claude/hooks/`，把配置片段合并进 `~/.claude/settings.json`；想只对一个项目生效，就放到 `<your-repo>/.claude/hooks/`，配置写进项目的 `.claude/settings.json`，命令改成 `python3 "$CLAUDE_PROJECT_DIR/.claude/hooks/guard.py"`。装好后运行 `python3 guard_test.py`，41 个用例全部通过时退出码为 0。hook 拦截的 git 写法：`reset`、`restore`、`revert`、`clean`、`stash`（`stash list`、`stash show` 放行），`checkout` 带 `--`、`.`、`-f`、`--force`、`-p`、`--patch`，`switch` 带 `--discard-changes`、`-f`、`--force`。安装步骤见 [INSTALL.md 第 2 步](../INSTALL.md#第-2-步-拦截钩子)。
- **怎样用到你的项目**：直接复制 hook 和测试；派子代理时同时使用 [templates/subagent-hard-rules.md](templates/subagent-hard-rules.md)，让禁令跟着转派传下去。

### 不把用户撤回的改动加回来

**规则原文**

> 用户经常会撤回或修改你的改动。你发现无法从上一次改动之后接着改时，先重新读取文件。例如你加了 A、B、C，用户删掉了 B，接下来的改动从“只有 A 和 C”的状态开始，不允许把 B 加回去。

- **防的是什么**：Agent 按自己记忆里的文件内容继续编辑，把用户已经删掉的东西又写回去。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。Claude Code 的编辑工具会在文件被外部改过后拒绝按旧内容编辑，这能挡住一部分情况。
- **怎样用到你的项目**：原样复制进全局规范。

### 多仓工作区里 git 分开操作

**规则原文**

> 工作区里有多个独立的 git 仓库时，git 命令在对应子目录里执行（或用 `git -C 【子目录】`），不跨仓提交；不合并这些仓库，除非用户明确要求做 monorepo 迁移。

- **防的是什么**：Agent 在父目录执行 git 命令，把一个仓库的改动提交进另一个仓库。
- **阿布里的来历**：阿布的工作区目录下面有客户端公开仓、企业版后台、私有仓三个独立仓库。规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：在工作区规范里列出每个子目录对应的仓库和远程。

### 并行工作互相隔离

**规则原文**

> 同一个 worktree 在实现期间只有一个负责人，其他并行任务只读。自主开发、尤其是碰私有仓的自主开发，一律在独立的 worktree 里运行，并先完成开发环境初始化。多个 worktree 不同时运行依赖安装和门禁命令，门禁串行进行。同一个检出里并发运行覆盖率时，每个进程设置独立的覆盖率输出目录。历史 worktree 不当作最新的开发入口，也不覆盖其中未提交的改动。

- **防的是什么**：两个 Agent 同时改同一个目录会互相覆盖；多个门禁同时运行会抢内存和端口，被对方拖累而显示失败；旧 worktree 里还有别人没提交的现场。
- **阿布里的来历**：规范写明多个 worktree 并发运行 `npm ci` 或 verify 会互相拖累、显示失败（提交钩子 30 秒超时）。2026-09-14 的夜间批次里，执行方给每个实现 worktree 只安排一个负责人，所有安装、测试、构建和提交钩子由执行方的会话按顺序分配时间窗口。
- **强度**：L1。门禁串行没有锁。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原样复制；并行任务多时，给门禁入口加一把文件锁。

### 不自动提交、推送和发布

**规则原文**

> 不自动 commit 或 push，等用户手动确认。未获用户明确批准，不发布更新源或 release 产物。

- **防的是什么**：Agent 觉得做完了就顺手提交推送，甚至发布；这些操作对外可见，撤回代价高。
- **阿布里的来历**：规范里未写明来历。阿布的夜间批次在交付说明里逐项写明“未推送、未合并、未开启自动合并”，由早上验收的人决定下一步。
- **强度**：L1。作者的 Codex 放行表直接放行了 `git commit`、`git push`、`gh pr merge`，与这条规则冲突，见文末缺口。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原样复制；同时检查 Agent 工具的放行表里没有放行提交、推送、合并命令。

## 代码写法

不写代码的读者可以跳过这一组。

### 只动该动的代码

**规则原文**

> 每一行 diff 都要能追溯到用户的请求，追溯不到的删掉再提交。改 A 时不顺手“优化”旁边的 B，不重构没坏的东西，匹配已有的写法。发现无关的无用代码或可疑代码，只提出来，不删；你的改动自己产生的无用 import、变量要删掉。

- **防的是什么**：Agent 喜欢顺手整理周围代码，diff 变大，复审看不清真正的改动，还会带进新的 bug。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则和复审。
- **怎样用到你的项目**：原样复制；复审时逐行核对 diff 能不能对应到需求。

### 出错就地失败

**规则原文**

> 代码要 fast-fail：在出错的位置直接报错退出，不捕获错误后假装成功，不做 fallback。

- **防的是什么**：Agent 为了让程序“能跑”，常用 try/catch 吞掉错误或返回默认值。问题被藏起来，要到很远的地方才以奇怪的形式出现。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原样复制；如果某些位置确实需要降级（例如网络不可用时显示离线界面），在规则后面列出这些允许的位置。

### 需要的依赖直接使用

**规则原文**

> 需要一个库，就直接 import 它；禁止用 try/except（或 try/catch）包住 import 做“有就用、没有就算了”。不为了少装依赖而绕开它，也不自己重写一个现成库已经提供的功能。

- **防的是什么**：可选导入让缺依赖的问题在运行时悄悄变成功能缺失；自己重写的轮子没有经过别人的测试。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原样复制。

### 成熟文件格式用现成的库解析

**规则原文**

> 不手写 parser 按字符串或字节去解析成熟的文件格式（JSON、YAML、TOML、CSV、XML、HTML、压缩包等）。要么用第三方库解析，要么不解析。

- **防的是什么**：手写的解析只覆盖 Agent 看到的几个例子，遇到转义、多行、编码差异就出错。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原样复制，可以在括号里补上你项目常见的格式。

### 标识符保持英文原名

**规则原文**

> 代码里的变量名、类名、函数名等所有 identifier 保持英文原名，写文档和回答时不翻译 identifier；适合用英文的专有名词也不翻译。

- **防的是什么**：把 `resolveEffectiveCreds` 写成“解析有效凭据”后，读者没法拿它去搜索代码。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：用非英文写文档的团队原样复制。

### 类型检查开启严格模式

**规则原文**

> TypeScript 全部开启 strict；不用有运行时语义的 `enum` 和 `namespace`，改用联合类型；不用 `any`，确实无法给第三方库写类型时，在那一行单独关闭规则并写明原因。

- **防的是什么**：`any` 和宽松模式让类型错误一路通过编译，到运行时才暴露。
- **阿布里的来历**：规范里未写明来历。ESLint 配置里的注释写着“规范禁止 any，要靠 lint 执行，不能只靠约定”。
- **强度**：CI L3；本地钩子 L2。CI 必需检查会运行 lint 和类型检查；本地提交钩子可以跳过。在代码里写 `eslint-disable-next-line` 注释可以逐行绕过。
- **执行机制**：tsconfig 的 `strict: true`、`erasableSyntaxOnly: true`；ESLint 把 `@typescript-eslint/no-explicit-any` 设为 error，规则见 [mechanisms/eslint-boundaries.mjs](mechanisms/eslint-boundaries.mjs)。
- **怎样用到你的项目**：在 tsconfig 打开这两项，把 `boundaryConfigs` 加进 ESLint 配置，并确认 CI 的必需检查里有 lint。

### 把代码约定写成 lint 规则

**规则原文**

> 能用 lint 表达的代码约定，就写成 lint 规则并设为 error：例如必须经过项目封装才能调用的第三方函数、只在 Node 进程运行的目录禁止使用浏览器全局变量、界面样式只用设计系统的设计变量。规则的报错信息里写清楚应该改用什么。

- **防的是什么**：写在规范里的约定，Agent 读过也会忘；lint 报错时它会当场改。
- **阿布里的来历**：阿布把多条约定写成了 ESLint 规则，下面三条是例子。
  - v0.41.0 发版后出现“误报有新版本”：更新插件自带的检查函数会把“更新器未启用”的标记包装成一个假的更新。之后 ESLint 禁止直接从该插件导入这个函数，所有检查必须经过项目自己的封装。
  - 后台进程的类型检查配置为了类型导入带了浏览器类型库，编译器发现不了后台代码误用 `window`，运行时才报“window is not defined”。之后 ESLint 在后台进程目录禁止 `window`、`document`、`localStorage` 等全局变量。
  - 界面字号只用 8 档设计变量、状态颜色只用语义化的设计变量、设计系统迁移名单里的文件只用新组件；2026-07 字号迁移完成后，靠 lint 让违规数保持为零。
- **强度**：CI L3；本地钩子 L2。字号、颜色、迁移名单规则在 CI 必需检查里运行；本地钩子一层都能用 `eslint-disable` 注释或 `--no-verify` 绕过；企业版后台的设计变量测试所在仓库没有分支保护。
- **执行机制**：[mechanisms/eslint-boundaries.mjs](mechanisms/eslint-boundaries.mjs) 提供其中两类的通用写法：`wrappedImports`（必须经过封装的第三方函数）和 `nodeOnlyFiles`（Node 进程目录禁止浏览器全局变量）。设计变量类规则与各项目的样式写法有关，参考阿布公开仓 `PM-Shawn/Abu-Cowork` 的 `eslint.config.js` 自己编写。
- **怎样用到你的项目**：每当复审时第二次发现同一类违规，就考虑把它写成 lint 规则；规则写好后补一个“规则确实会报错”的自测（阿布用 ESLint API 验证设计规则真的报错）。

### 界面进程不直接调用系统能力

适用于 Electron 这类“界面进程 + 特权进程”结构的桌面应用。

**规则原文**

> 界面进程的代码（例如 `src/`）不直接使用 Node、`fs`、`child_process`、shell 或原始进程接口。需要新能力时，经过 preload → 主进程（或独立的后台进程）暴露，并在特权一侧校验输入。

- **防的是什么**：界面进程里直接能读写文件、启动进程，一旦界面加载了不可信内容，就等于把系统权限交出去。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。阿布的 ESLint 对 `src/` 只限制了更新插件和设计系统的导入，界面进程导入 `fs`、`child_process` 时只有复审能发现。
- **执行机制**：[mechanisms/eslint-boundaries.mjs](mechanisms/eslint-boundaries.mjs) 的 `forbiddenModulesInApp` 参数（例如传入 `['fs', 'child_process']`）会同时禁止 `fs` 和 `node:fs` 两种写法。阿布还没有启用这一项。
- **怎样用到你的项目**：把界面进程目录填进 `appFiles`，把不允许的模块填进 `forbiddenModulesInApp`。

### 跨平台代码不假定路径格式和 shell

**规则原文**

> 同时支持 macOS 和 Windows 的代码：用项目统一的平台判断和路径工具函数，不把路径分隔符、用户目录写进代码；新增的命令安全或路径安全规则，两个平台都要加；不假定用户用的是某一种 shell。

- **防的是什么**：Agent 多在一个平台上开发和测试，另一个平台的路径和命令问题要到用户那里才暴露。
- **阿布里的来历**：规范里未写明来历。阿布的做法是统一使用 `platform.ts` 与 `pathUtils.ts`，`commandSafety`、`pathSafety` 的新规则两个平台一起加。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：把规则里的“项目统一的工具函数”换成你项目里实际的文件名。

### 迁移后旧技术只保留兼容

**规则原文**

> 从旧技术迁移到新技术之后，只在新技术上开发、调试和验收新功能。旧技术的代码只保留已发布版本的兼容、数据迁移和回退证据，不再加新功能，在旧技术上运行通过也不算验收。数据迁移只读取旧数据、写完才标记完成，失败就在界面出现前停下、下次重试；过渡期保留旧版本的数据和安装目录，让用户能退回。

- **防的是什么**：Agent 读到仓库里还在的旧代码，会继续往上面加功能，或者用旧技术跑通就声称完成。
- **阿布里的来历**：阿布的桌面壳从 Tauri 迁到 Electron。规范规定 Electron 是唯一的开发、调试、验收桌面壳，Tauri 只保留兼容与迁移，Web 预览也不算桌面验收。首次启动时的迁移只读 Tauri 数据，写完完整的完成标记文件才算完成；Windows 保留旧安装目录一个版本，卸载新版本也不删它。旧的 `npm run tauri*` 命令改成直接报错并指向 Electron，见 [01-方向：退役的入口改成报错指路](../01-方向/README.md#退役的入口改成报错指路)。
- **强度**：规范 L1；迁移代码 L3。“只读、写完才算完成”由代码逻辑执行；Windows 保留回退目录在发版构建里有安装后检查；macOS 退回要人工重装旧版本，这一项 L2。
- **执行机制**：暂无可复制文件，迁移代码与具体技术绑定。
- **怎样用到你的项目**：迁移完成时把这条规则写进规范，并把旧入口改成报错指路。

### 改持久化结构要升版本并写迁移

**规则原文**

> 改动本地持久化数据（例如状态库）的结构时，升版本号、写从每个旧版本开始的完整迁移，并更新版本登记测试。数据库迁移只增不改、按编号顺序，用工具生成；手写的迁移要能重复执行而不出错。容器启动时自动执行迁移的项目，要知道迁移执行后未必能降级。

- **防的是什么**：结构变了却没写迁移，老用户升级后数据读不出来或被清空。
- **阿布里的来历**：客户端的状态库持久化到本机，有一个版本登记测试逐个核对每个状态库的版本。企业版后台的数据库迁移在 2026-08-13 重新生成过一份起点；镜像启动时会自动执行迁移，部署文档写明迁移后未必能降级。
- **强度**：版本登记测试 L2；数据库迁移规则 L1。容器启动自动迁移的那一步由代码执行，启动即运行。
- **执行机制**：版本登记测试的做法是维护一张“持久化键名 → 最低版本”的表。测试加载全部状态库后检查两件事：每个持久化键都登记在表里，新加的状态库没登记就失败；每个状态库写出的版本不低于登记的最低版本。
- **怎样用到你的项目**：给每个持久化结构加版本号和登记测试；数据库迁移交给迁移工具生成。

### 源文件不含 NUL 字节

**规则原文**

> 源文件里不写原始 NUL 字节；需要这个值时写转义 `\x00`。

- **防的是什么**：git 看到文件开头附近有 NUL，就把整个文件当成二进制，diff 和 PR 里只显示字节数，改动内容谁也看不到。
- **阿布里的来历**：阿布有三个源文件带了原始 NUL，功能正常、测试全绿，但在 diff 里只显示“Bin 12614 -> 30636 bytes”。其中两个是插件的 git 拉取和 MCP 工具审批，恰好是最需要逐行复审的文件。
- **强度**：L2。作为全量测试的一部分运行，不运行就不检查。
- **执行机制**：[mechanisms/check-nul-bytes.py](mechanisms/check-nul-bytes.py)。
- **怎样用到你的项目**：修改脚本里的源文件后缀，把它放进本地门禁命令和 CI。

## 保密

### 密钥只放在本机

**规则原文**

> 密钥、登录 token 和 `.env`、`.env.local` 文件不提交、不写进源码；这些文件必须写进 `.gitignore`。公开仓的提交里不带内部信息、签名材料、客户数据和内部 URL。

- **防的是什么**：密钥一旦进了 git 历史，删除文件也没用，只能作废重发；公开仓里的内部信息会被任何人看到。
- **阿布里的来历**：规范里未写明来历。阿布的工作区目录用“默认全部忽略、逐条放行”的 `.gitignore`，新文件必须有人明确放行才会进版本库。
- **强度**：L2。`.gitignore` 会忽略这些文件，但 `git add -f` 可以绕过，也没有扫描提交内容的检查。
- **执行机制**：[mechanisms/gitignore.snippet](mechanisms/gitignore.snippet)（含可选的“默认全部忽略”写法）。
- **怎样用到你的项目**：把片段加进每个仓库的 `.gitignore`；需要更强的保护时，另加按内容扫描密钥的工具。

### 不用带本机密钥的环境打对外分发包（可选）

适用于构建时会把环境变量编进产物的项目，例如 Vite 的 `VITE_*` 变量。

**规则原文**

> 绝不用带 `.env.local` 的本机环境打对外分发的安装包；构建时注入的前端变量会编进产物，任何人都能从安装包里取出来。官方包只由 CI（没有本机密钥）构建。需要为特定客户出包时，客户配置由私有构建任务提供，构建脚本检查所在目录里没有 `.env*` 文件、没有无关的构建变量，不满足就退出。

- **防的是什么**：开发者在自己机器上顺手打一个包发出去，把观测服务的密钥一起发给了所有用户。
- **阿布里的来历**：阿布的观测服务密钥只放在 `.env.local`，缺密钥时观测功能不工作，开源版默认不采集任何数据。客户专用构建脚本会拒绝所在目录里的 `.env*` 文件和无关的 `VITE_*` 变量。
- **强度**：规范 L1；构建脚本 L2。构建脚本必须通过规定的 npm 命令运行，直接调用底层命令可以绕过。
- **执行机制**：暂无可复制文件，检查项与构建工具有关。
- **怎样用到你的项目**：在发版清单写明“对外分发包只由 CI 构建”；有客户定制构建时，在构建脚本开头加上环境检查。

### 服务端处理机密和权限的默认做法

**规则原文**

> 所有受保护的接口一律用项目统一的鉴权包装，不在路由里手写鉴权；权限用常量表达，统一返回 401、403、500。新增的受保护接口默认带权限约束和限流。登录 token、密钥、密码、refresh token 不写进日志。存进数据库的机密用 AES-GCM 加密。

- **防的是什么**：Agent 新写一个接口时漏掉鉴权或权限检查，或者为了排查问题把登录 token 打印进日志。
- **阿布里的来历**：企业版后台的规范。规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则和安全复审。
- **怎样用到你的项目**：把“统一的鉴权包装”换成你项目里实际的函数名。

### 遥测默认关闭并脱敏（可选）

适用于采集使用数据的产品。

**规则原文**

> 面向终端用户的线上遥测必须由用户主动开启（opt-in），经服务端中转（密钥不下发到客户端），并且脱敏。埋点只传事件名和枚举或分桶后的属性，不传任何用户内容和个人信息。事件写进自己的事件表和接口，复用已有的事件名白名单和频率上限，不接第三方分析 SDK。

- **防的是什么**：Agent 为了“方便分析”，把用户输入的原文或文件路径一起上报。
- **阿布里的来历**：客户端规范写“开源版默认零采集，线上遥测必须 opt-in”；运营后台规范写埋点只传事件名和枚举属性、不接第三方分析 SDK。两处对默认值的写法不一致，见文末缺口。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：先定下默认开还是关，写进所有相关仓库的规范，只保留一种说法。

### 公开仓与私有仓分开（可选）

适用于核心开源、商业功能闭源的 open-core 项目。

**规则原文**

> 闭源实现只写在私有仓。公开仓只放“形状”：扩展点接口、空插槽、编译期转发文件、开源版的空实现和构建开关；任何网络请求、凭据保存、策略判断和闭源界面都属于私有仓，闭源功能的测试也不进公开仓。build 和 test 全绿不代表没有泄露。私有仓与公开仓放在同级目录；私有仓的 CI 固定使用公开仓的某一个提交作为运行环境，更新要刻意进行；私有仓的测试只断言需求，不绑定公开仓的某种布局，公开仓改动合入后尽快合入私有仓的配套改动。

白话说法：公开仓里只留插座，插头和电器都在私有仓。

- **防的是什么**：闭源代码一旦推送进公开仓，git 历史里就清除不掉；这类问题编译检查不出来。
- **阿布里的来历**：阿布在 2026-08-06 完成了公开仓与私有仓的边界迁移。公开仓的泄露检查脚本注释写明：泄露属于保密问题、编译发现不了、推送到公开历史就无法清除。另一个教训：一个公开模块不再导出的类型，在闭源构建里出了错，却通过了审查，所以阿布加了只在手动时运行的闭源构建类型检查。
- **强度**：CI L3；本地 L2。公开仓 CI 的泄露检查汇总进必需检查，但它只按文件名和路径名单拦截：换个文件名的闭源代码拦不住；它只在推送之后由 CI 运行，本地没有 npm 脚本、不在提交钩子、不在门禁命令里，见文末缺口。
- **执行机制**：[mechanisms/leak-guard/](mechanisms/leak-guard/)：
  - [public-leak-guard.sh](mechanisms/leak-guard/public-leak-guard.sh)：按名单扫描已跟踪和未跟踪（未被忽略）的文件，命中就以退出码 1 失败；名单缺失、为空，或者还留着示例里带尖括号的占位条目，以退出码 2 失败。
  - [leak-guard-paths.example](mechanisms/leak-guard/leak-guard-paths.example)：名单文件格式，用占位写法；原样复制不改时检查会失败并提示“名单还是示例内容”。
  - 提交钩子：全材料只有一份 pre-commit，即 [02-判定 的 husky-pre-commit](../02-判定/mechanisms/husky-pre-commit)。文件里有一行注释掉的 `npm run check:leak`，排在 `npx lint-staged` 前面，去掉注释就接入了。
  - [leak-guard.ci.yml](mechanisms/leak-guard/leak-guard.ci.yml)：CI job 片段，加进 `ci.yml`；并入汇总必需检查 `check` 时要同步改的三处写在文件开头。
  - [leak-guard.test.sh](mechanisms/leak-guard/leak-guard.test.sh)：在指定的空目录里建一个临时仓库，核对 12 种情况的退出码，包括提交钩子能挡住提交。
- **怎样用到你的项目**：写好名单文件，在 package.json 加 `"check:leak": "bash scripts/public-leak-guard.sh"`，在提交钩子、门禁命令、CI 三处运行它（逐步做法见 [INSTALL.md 的可选机制](../INSTALL.md#可选机制)）；在规范里保留“公开仓只放形状”这条，靠复审把关文件内容。

## 分支与合并

### 叠放 PR 不提前开自动合并

**规则原文**

> 叠放 PR（base 是另一个特性分支）绝不提前开 auto-merge。顺序是：父 PR 合入集成分支 → 把子 PR 的 base 改成集成分支 → 把最新的集成分支合进子分支 → 本机跑门禁 → push → 再开 auto-merge。改 PR base 不会触发 CI，改完必须再 push 一个提交或关闭再重开，让必需检查重新运行。

- **防的是什么**：`gh pr merge --auto` 只有在 base 分支有保护时才会“排队等条件”；base 是没有保护的特性分支时，它会立即合并。
- **阿布里的来历**：2026-09-06 事故：子 PR 的 base 是没有分支保护的父特性分支，提前开的 auto-merge 把子 PR 立即合进了父分支，整条叠放顺序错位一格。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原样复制；“改 base 后重新触发 CI”那半条属于判定制度，见 [02-判定](../02-判定/README.md#改了-pr-的目标分支要重新触发检查)。

### 发版分支只接受快进

发版分支只能原样跟上集成分支，不能单独挑几个修改复制过去。复制过去的修改内容相同、编号不同，以后两条分支合并时会出现大量假的冲突。

**规则原文**

> 集成分支是唯一集成线，功能和修复分支从最新的集成分支创建，PR 回集成分支。发版分支只接受从集成分支 fast-forward（快进），禁止在发版分支上直接开发、commit、push，禁止 cherry-pick、squash、rebase 生成“内容相同、提交号不同”的提交。热修从对应 tag 拉分支定位问题，修复先 PR 进集成分支，再按同样的快进流程发布。已经退役的分支不再用来创建新分支。

- **防的是什么**：cherry-pick 会让两条分支的历史发散，下次合并满屏假冲突，逼人继续 cherry-pick，越滚越大。
- **阿布里的来历**：2026-07，阿布的 dev 与 main 因为 cherry-pick 分叉到 223 和 124 个提交，靠一次收敛合并才解开。之后加了一项 CI 检查，核对 main 的提交是否都包含在 dev 的历史里。
- **强度**：L3。发版分支的分支保护登记了汇总检查和快进检查，并开启“管理员也不能绕过”。“功能分支从最新集成分支创建”“只接受从集成分支开 PR”“tag 必须打在发版分支上”这三项没有必需检查，见文末缺口。
- **执行机制**：[mechanisms/branch-policy.yml](mechanisms/branch-policy.yml)（集成分支每次推送后检查发版分支是否是它的祖先，检查名 `promotion-ready`），加上分支保护设置。
- **怎样用到你的项目**：复制 workflow，改分支名，在分支保护里登记 `promotion-ready` 为发版分支的必需检查。

### 主要分支禁止强制推送

**规则原文**

> 不 `git push --force` 到集成分支或发版分支，除非用户明确要求。

- **防的是什么**：强制推送会覆盖别人已经推送的提交。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L3。两个分支的保护都关闭了强制推送。
- **执行机制**：GitHub 分支保护的“禁止强制推送”“禁止删除”选项。
- **怎样用到你的项目**：在分支保护里打开这两项。

### 两条产品线互不合并

**规则原文**

> 同一个仓库里有两条用途和部署通道都不同的产品线时，两条线永远不整体合并，只 cherry-pick 共享的修复；一条线的分支绝不推送到另一条线的主分支。动手前先核对远程地址、分支名和该分支自己的规范，不能凭本地目录名判断自己在哪条线上。长期打算是把其中一条线独立成仓。

- **防的是什么**：误推送会触发另一条线的 CI 和部署，还会带进一批对方没有部署过的提交。
- **阿布里的来历**：阿布的企业版后台和运营后台是两条产品线，2026-08-09 定下这条规矩。其中一条线的分支上仍留着一份旧的部署 workflow，只要推送到另一条线的主分支就会触发，所以规范写“绝不能推送到主分支”。
- **强度**：L1。对应仓库没有分支保护，误推送不会被拦下，见文末缺口。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：能开分支保护就开；在每条线的规范开头写清楚“本线是什么、PR 回哪个分支、绝不推送到哪个分支”。

## 部署

### 版本标签单独推送

**规则原文**

> 发版时单独推送一个 tag：`git push origin vX.Y.Z`；不用 `git push origin main --tags`。

- **防的是什么**：一次推送超过 3 个 tag 时，GitHub 不触发 tag 事件，发版 workflow 不会运行。
- **阿布里的来历**：发版文档写明了上面这条 GitHub 行为。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原样写进发版清单。

### 发版交给流水线

**规则原文**

> Release 交给 CI 完成整套流程：不手工创建重复的 Release；workflow 运行期间不删除、不重建、不手动发布草稿。

- **防的是什么**：人工和流水线同时操作同一个 Release，状态互相覆盖，失败后的自动还原也会失效。
- **阿布里的来历**：阿布的发版流水线在“写更新源 → 公开 Release”这一段失败时会整体还原；人工插手会破坏这个前提。规范里未写明具体事故。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原样写进发版清单。

### 线上更新源的版本不回退

**规则原文**

> 发布前读取线上更新源当前的版本；线上版本比候选版本新时拒绝写入。

- **防的是什么**：排队中的旧 tag 晚于新 tag 运行，把线上更新源改回旧版本。
- **阿布里的来历**：发版流水线在写更新源之前运行版本比较脚本，旧 tag 在这里失败。
- **强度**：L3。在发版流程里，失败就不会进入写入步骤。
- **执行机制**：暂无可复制文件，脚本读取的更新源格式与项目有关。做法是：读线上版本、与候选版本比较、候选不更新就退出码非零。
- **怎样用到你的项目**：在写更新源或下载页元数据之前加这一步。发现坏版本时只能再发一个更高的版本，要在发版清单里写明。

### 非官方构建拿不到官方更新（可选）

适用于带自动更新的桌面应用。

**规则原文**

> 从源码或 fork 构建的包不带“官方构建”标记、不带生产环境的更新配置。打包版只有带官方标记时才启用更新，并且只读取包内自带的更新配置，忽略环境变量里的更新地址。

- **防的是什么**：别人 fork 后保留了同一个应用 ID，就能拿到官方更新；环境变量可以被外部脚本改写，把更新源换成别的地址。
- **阿布里的来历**：更新器代码里的注释写明了上面两点。
- **强度**：规范 L1；更新器代码 L3。更新器的启用条件是代码逻辑，用户改不了。
- **执行机制**：暂无可复制文件，与更新框架有关。
- **怎样用到你的项目**：在打包流程里只让 CI 写入官方标记。

### 镜像在 CI 构建，服务器只加载

**规则原文**

> 绝不在生产服务器上构建镜像。镜像由 CI 构建，以文件形式传到服务器后加载，只重建需要更新的那个服务；不直接运行不带服务名的 `docker compose up -d`。新增的部署分支要先加进构建 workflow 的触发列表。

- **防的是什么**：在内存较小的服务器上构建会耗尽内存，整机失去响应，连 SSH 都登不上去补救；不带服务名的 `up -d` 会把编排文件里所有服务都拉起来。
- **阿布里的来历**：企业版部署的服务器上真实发生过一次构建时整机不可用。运营后台因此只保留一条部署通道：CI 构建镜像 → 下载构建产物 → 经 ssh 传输 → 服务器加载 → 只重建应用容器。
- **强度**：L1。仓库里仍有按旧做法（服务器拉代码、服务器构建）部署的脚本，见文末缺口。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：把部署步骤写成脚本，脚本里只出现带服务名的重建命令；删掉旧的部署脚本。

### 生产部署安全清单（可选）

适用于自己托管服务端的项目。

**规则原文**

> 生产部署：由反向代理处理 TLS；`.env` 权限 600，存放许可证等敏感文件的目录权限 700；只开放 80 和 443 端口；每天备份数据卷；怀疑密钥泄露时轮换主密钥；审计日志按合规要求的期限保留。

- **防的是什么**：部署时只关心“能跑起来”，忽略文件权限、端口和备份。
- **阿布里的来历**：部署文档里的安全清单。规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：按你的部署方式改写每一项，放进部署手册。

### 修数据的脚本默认只读

**规则原文**

> 检查和修复数据的脚本默认只读，只输出发现的问题；真正写入必须同时给出修复计划参数、执行参数和确认参数。

- **防的是什么**：Agent 为了看看结果运行一次修复脚本，直接改了生产数据。
- **阿布里的来历**：企业版后台检查部门上下级关系的脚本采用这个设计，写入需要同时给 `--repair-plan`、`--apply`、`--yes`。
- **强度**：L2。
- **执行机制**：暂无可复制文件。
- **怎样用到你的项目**：新写数据修复脚本时照这个参数设计。

## 测试环境

### 启动前检查开发环境

**规则原文**

> 启动开发环境前先检查依赖和构建产物是否齐全、版本是否与锁文件一致；缺东西就停下，给出修复命令，不临时下载，也不带着不完整的依赖启动。新 worktree 用专门的初始化脚本安装依赖；依赖目录是链接到其他 worktree 的共享目录时，拒绝安装。

- **防的是什么**：缺依赖或产物过期时照样启动，测到的是旧代码，Agent 却以为验收通过；在共享的依赖目录上重新安装，会把其他 worktree 的依赖删改掉。
- **阿布里的来历**：阿布的开发壳启动前自动运行预检（锁文件、原生模块、各类运行时和产物）；初始化脚本在依赖目录是符号链接时拒绝安装，原因是避免 `npm ci` 删改其他 worktree 共享的依赖。
- **强度**：L2。用 `--ignore-scripts` 或直接调用底层启动命令可以绕过。
- **执行机制**：暂无可复制文件，检查项与项目的依赖结构绑定。
- **怎样用到你的项目**：把“启动命令”做成 npm 脚本，用 `pre` 脚本先运行预检。

### 安全边界测试放进必需检查

**规则原文**

> 权限、文件系统、进程间通信输入校验这类安全边界的测试单独成一组，并在每个 PR 的必需检查里运行。

- **防的是什么**：安全边界回归不在 PR 检查里，就会先合入集成分支，到发版构建时才被发现。
- **阿布里的来历**：阿布的一组安全边界测试（插件拉取与快照、文件系统、电脑操控权限、附件、IPC 原始包体等）盘点时只在手动触发或发版调用的构建 workflow 里运行，不在 PR 必需检查、不在门禁命令里。
- **强度**：L2。把它放进必需检查的补强见文末缺口。
- **执行机制**：暂无可复制文件。
- **怎样用到你的项目**：给安全相关测试一个单独的 npm 脚本，放进 CI 的汇总必需检查。

### 覆盖率阈值只升不降

**规则原文**

> 覆盖率阈值只写在测试配置文件（`vitest.config.ts`）一处，文档不重复具体数字。阈值取实测值向下取整再减 2 个点，核心目录单独设下限。不开自动更新阈值的选项（`autoUpdate`）；只在一个专门的提交里手动调高，不调低；把测试移进隔离区造成的缺口也不能靠调低阈值解决。

- **防的是什么**：Agent 遇到覆盖率门禁变红，最省事的办法是把阈值改低；覆盖率一点点往下掉而没人发现；`autoUpdate` 每次运行都改写配置文件，弄脏工作区。
- **阿布里的来历**：配置注释写明不开 `autoUpdate` 的原因：它会改动被跟踪的配置文件，破坏自主循环“`git status` 为空”的完成条件，还会把阈值定在小数上，覆盖率有不到 1% 的波动就误报失败。
- **强度**：规范 L1；阈值检查 L2。覆盖率低于阈值时 CI 变红，但调低阈值本身没有任何检查，见文末缺口。
- **执行机制**：[05-进化 的 vitest.coverage-thresholds.ts](../05-进化/mechanisms/coverage/vitest.coverage-thresholds.ts)（阈值与 reporter 的写法；按目录的下限键要写成 glob，例如 `'src/core/**'`）。
- **怎样用到你的项目**：按片段里的注释填入你的实测值；复审时把“改了阈值配置”列为必须说明理由的改动。

### 不稳定测试走隔离流程

**规则原文**

> 随机失败的测试走隔离流程：开一个标记为 `flaky-test` 的 issue 写清复现办法；Vitest 文件移进隔离目录，第一行写 `// QUARANTINED: 【issue 链接】 (YYYY-MM-DD)`；Playwright 用 `test.fixme(true, 'QUARANTINED: 【issue 链接】 (YYYY-MM-DD)')`。不用 retries、`it.skip`、`vi.retry()`、`waitForTimeout` 掩盖失败；E2E 配置保持 `retries: 0`，CI 里禁止 `test.only`。隔离最长 4 周，超期后由主门禁里的一个检查测试变红，只能修好移回或者删掉；检查用的截止日期由 CI 注入当天日期。E2E 的模拟数据按上一步的真实结果推进，触发操作前先等待对象就绪。

- **防的是什么**：加重试或跳过会把真实的失败藏起来，大家习惯忽略红色；隔离区变成永久的垃圾堆。
- **阿布里的来历**：2026-06-30 阿布隔离了第一批测试。检查测试当时用的截止日期正好等于隔离日期，时钟没有前进，超期了也没人发现，直到 2026-09-02 才被删除。之后改为 CI 注入当天日期，日期格式错误时直接报错，不退回固定日期。公开仓 issue #362、#389、#394 暴露的 E2E 模拟数据问题，促成了“按真实结果推进、先等就绪”的规则。
- **强度**：客户端 CI L3；本地 L2。期限检查在客户端 CI 里注入当天日期，超期就变红；本地用代码里的固定日期，永远不会因为超期变红；`retries: 0` 和 `forbidOnly` 写在配置里，可以被改掉；企业版后台没有 CI 注入日期。
- **执行机制**：[05-进化 的 quarantine/](../05-进化/mechanisms/quarantine/)：检查测试 `quarantine-sla.test.ts`、截止日期解析 `quarantineAsOf.ts`、Playwright 标记检查 `specQuarantine.ts`、隔离测试专用配置 `vitest.quarantine.config.ts`、CI 注入日期的片段 `ci-quarantine-asof.yml`。Playwright 配置写 `retries: 0`、`forbidOnly: !!process.env.CI`。
- **怎样用到你的项目**：复制四个文件，主配置排除隔离目录，CI 的测试 job 加上注入日期的一步（逐步做法见 [INSTALL.md 的可选机制](../INSTALL.md#可选机制)）；在 Playwright 配置里加上那两项；把目录名和标记格式换成你的。

### 测试环境固定，不靠放宽条件过关

**规则原文**

> 测试宿主的语言、地区等环境值固定；切换语言的测试在结束时还原。不全局调高测试超时；个别确实慢的测试单独给超时，并附上证据。

- **防的是什么**：测试结果随运行机器的系统语言变化；为了让随机超时的测试通过，把所有测试的超时都调高，真正卡住的测试也被掩盖。
- **阿布里的来历**：在中文 Windows 上，18 个文件的 95 个测试读到了中文，之后固定为 en-US。2026-08-21 修复 verify 中四个测试随机变红时，定下“不全局调高 testTimeout”。
- **强度**：语言固定 L2；超时规则 L1。语言固定由一个检查固定值的测试执行；还原与否、超时规则没有检查。
- **执行机制**：做法是写一个测试，断言测试环境里的语言等于固定值。
- **怎样用到你的项目**：在测试的全局 setup 里固定语言和时区。

### 测试文件保持短小

**规则原文**

> 单个测试文件不超过 200 行；测试里不用 `console.log`。

- **防的是什么**：测试文件越写越长，失败时难以定位；测试输出里夹着调试打印。
- **阿布里的来历**：企业版后台的测试规范。规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：原样复制，行数上限按项目调整。

## 阿布专属规则示例

下面这些规则与阿布使用的框架或目录结构绑定，提炼不出通用写法，只作为“规范可以写到多具体”的例子。

| 规则 | 为什么阿布需要它 |
|---|---|
| 界面文字走 i18n，新增文案先加进 `TranslationDict` 类型再补两种语言 | 界面有中英两种语言，缺一种语言的 key 会让类型检查失败 |
| 代码、注释、提交信息用英文；LLM system prompt 和工具描述用英文，回复语言由单独的配置段控制 | 公开仓面向国际贡献者；回复语言跟随界面语言，与 prompt 语言无关 |
| React 组件只用函数组件、一个文件一个主导出；Hook 清理所有副作用；核心模块接口先行、错误类带分类；不在 `index.css` 加样式 | 统一代码写法，降低 Agent 生成代码的风格差异 |
| 测试与源码同目录、全局 mock 放在 setup 文件；DOM 测试在首行单独开启 happy-dom，不把全局默认改回 | 全量测试耗时从约 71–75 秒降到约 42–55 秒 |
| 被 mock 的模块不在同一模块里并发 `await import()` | 2026-09-11 用探针 5 次复现 5 次的随机失败 |
| 新窗口一律经 `revealWindow()` 显示，不直接 `win.show()` | E2E 运行时 `revealWindow()` 改用不抢焦点的显示方式；直接 `win.show()` 会让应用在整个测试期间抢走开发者的键盘焦点 |
| 跨仓共享的接口样本文件，各仓副本与规范副本逐字节比对 | 各仓 CI 独立检出，读不到工作区目录，只能各自带一份副本 |

## 还没补上的缺口

| 问题 | 后果 | 打算补的机制 |
|---|---|---|
| 公开仓泄露检查只看文件名，并且只在推送之后运行 | 闭源代码换个文件名、或写进公开文件里，检查就拦不住；一旦推送进公开仓，历史清除不掉 | 提交钩子和门禁命令第一步运行同一条检查（阿布的 PR #599 已开，尚未合入），并补充按内容判断的规则 |
| 部分仓库没有分支保护 | CI、PR 复审策略、提交信息检查都只做参考；误推送到主分支时不会被拦下 | 开启分支保护 |
| 旧的部署脚本仍然存在：仓库里还留着“服务器拉代码、服务器构建、不带服务名启动”的部署 workflow 和脚本 | 与现行部署规矩冲突，误推送或照着操作就会用旧方式部署 | 删除过时的脚本和文档（需要作者决定） |
| 版本 tag 不检查所在提交 | 任何有写权限的人在任意提交上推送一个格式匹配的版本 tag，就会完整发布；发布成功后不能回退，只能再发更高版本 | 预检里校验 tag 指向的提交在发版分支上（阿布的 PR #600 已开，尚未合入） |
| Agent 工具层面的禁令只拦了一部分：Claude Code 侧的 hook 已经拦截 git 回滚和 /tmp 读写，但“不用程序化方式改代码”“不擅自进入 plan mode”仍靠模型自觉；Codex 放行表全部是 allow | Codex 可以不经确认提交、推送、合并 | 扩展 hook 规则；为 Codex 加禁止规则（需要作者决定 Codex 能否自动提交推送） |
| 安全边界测试不在 PR 必需检查里；闭源构建的类型检查也不在门禁命令里 | 安全回归可以合入集成分支，到发版构建时才发现 | 安全测试放进汇总必需检查（阿布的 PR #602 已开，尚未合入） |
| 调低覆盖率阈值没有任何检查 | 阈值被改低时不会有检查变红 | CI 检查阈值不得低于 base 分支 |
| 界面进程禁用系统模块没有 lint 规则 | 界面代码直接导入 `fs`、`child_process` 时只有复审能发现 | `no-restricted-imports`（见 [mechanisms/eslint-boundaries.mjs](mechanisms/eslint-boundaries.mjs)） |
| 同一件事在不同规范里写法相反：遥测默认开还是关、注释用中文还是英文、Agent 能否自动提交推送，各有两处规范给出相反要求 | Agent 按读到的文件得到不同指令 | 由作者决定后只保留一种说法 |
| 客户端规范里仍有旧桌面框架时期的规则：个别小节还要求使用已经只保留兼容的旧框架的路径接口 | 与“新功能只在新框架上开发”冲突 | 删除过时内容 |
| /tmp 仍写在标准流程里：部署手册、发版文档、任务书把 /tmp 写进标准命令，多份交付说明的证据在 /tmp；`.scratch/` 只写进了工作区目录的 `.gitignore`，子仓库都没有 | 重启后证据丢失 | 任务书模板改用 `.scratch/`，各仓库补 `.gitignore` |
| 旧的夜间计划要求直接提交并推送主分支，这份旧计划仍留在多个检出目录里 | Agent 读到后可能照做，而对应仓库没有分支保护 | 删除过时内容 |
| 门禁串行没有机制 | 多个 worktree 同时运行依赖安装或门禁会互相拖累、显示失败 | 门禁入口加锁 |

## 作者的个人习惯

下面这些规则来自作者自己的全局规范，反映作者个人的工作习惯和对回答方式的要求。读者按自己的情况取舍。

### 规则没有例外

**规则原文**

> 本文件中的每一条规则都强制执行，没有例外和豁免：临时的、一次性的、命令行上的违反同样算违反；没被当场发现也算；出于好意、为了进度的违反也算。

- **防的是什么**：Agent 常以“这次只是临时”“为了先跑通”为理由破例。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：放在全局规范开头。

### 不读写 /tmp，中间结果放进仓库

**规则原文**

> 禁止读写 /tmp 目录。中间结果统一输出到当前仓库根目录的 `.scratch/` 目录，该目录必须写进 `.gitignore`。

- **防的是什么**：交付说明里引用的日志和截图放在 /tmp，机器重启或系统清理后证据就没了。
- **阿布里的来历**：多份任务书和交付说明把门禁日志、证据放在 /tmp（例如“门禁输出重定向到 /tmp/v.log”），部署脚本也把旧镜像 ID 记在 /tmp。
- **强度**：装了钩子的 Claude Code L2；其他工具 L1。2026-09-30 起，Claude Code 侧由同一个 PreToolUse hook 拦截命令和文件工具里的 /tmp 路径；Claude Code 自己放附件的目录只放行读取。Codex 不受约束。
- **执行机制**：[mechanisms/claude-code-guard/guard.py](mechanisms/claude-code-guard/guard.py)、[mechanisms/gitignore.snippet](mechanisms/gitignore.snippet)。
- **怎样用到你的项目**：每个仓库都加 `.scratch/` 到 `.gitignore`；任务书模板里的日志路径改成 `.scratch/`。

### 不用程序化方式修改代码

**规则原文**

> 不用 heredoc、Python 脚本、sed、perl 等程序化方式修改任何代码，只用文件编辑工具。

- **防的是什么**：批量替换会改到不该改的地方，而且改了什么不经过逐处确认。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。hook 目前没有拦截这一类，见上文缺口。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：需要大批量机械改动的项目可以不采用，改为“批量改动后必须跑门禁并逐项复审 diff”。

### 不擅自进入 plan mode

**规则原文**

> 除非用户明确要求，禁止擅自进入 plan mode。

- **防的是什么**：用户已经给了明确的指令，Agent 却停下来写计划等待批准。常见情形是用户说“把这个函数的参数改成可选的”，Agent 回了一页计划问“可以开始吗”。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：按自己的习惯决定。

### 回答的写法

**规则原文**

> - 没有被要求对比时，不用先否定一方再肯定另一方的句式。
> - 读代码之前，不说“我先做 x，再做 y，避免 z”。
> - 搜索时不列出被排除的无关结果。
> - 回答不写总起句和总结句。
> - 被指出错误后不复述错误原因，直接在正确的前提下继续。
> - 用户以疑问句结尾时只回答问题，不附带新方案、不反问、不说“准备好就开始”。
> - 不评价工作量，不简化设计。

- **防的是什么**：回答里的套话、铺垫和自我评价占掉读者的注意力。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。

### Agent 工具的放行配置

这一条是现状记录。阿布的规范里没有这条规则，盘点记录的是下面的现状：

> 作者的 Codex 命令放行表有 161 条，全部是 allow，其中包括 `git commit`、`git push`、`gh pr create`、`gh pr merge`、`git pull` 和多条 /tmp 操作，没有任何禁止规则。Codex 默认模型与推理强度写在 `~/.codex/config.toml`。Claude Code 的项目级权限放行 `npm run *`、`npx vitest *` 等命令。

- **强度**：L0。“只放行只读命令”这条在阿布没有写进任何文件，现有的放行表与它相反，Agent 想提交、推送时没有任何东西拦它。放行表与“不自动提交推送”“不读写 /tmp”两条规则冲突，见上文缺口。
- **执行机制**：[mechanisms/codex-default.rules.example](mechanisms/codex-default.rules.example)（Codex 放行表示例，只含只读命令和门禁命令）、[mechanisms/claude-permissions.snippet.json](mechanisms/claude-permissions.snippet.json)（Claude Code 项目级权限片段；`npm run *` 会放行所有 npm 脚本，包括发版类脚本，按需收窄）。

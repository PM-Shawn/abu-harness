# 常用词解释

模板仓库里反复出现的词，这里每条用一句白话解释。正文里第一次出现关键词时也带了半句说明，其余的在这里查。

## 和 AI 有关

| 词 | 白话解释 |
|---|---|
| Agent | 能自己动手的 AI：除了聊天，还会读文件、改代码、运行命令 |
| harness | 套在 Agent 身上的整套规矩和检查 |
| 会话 | 和 AI 的一次连续对话；新开一个会话，它不记得上一个会话的内容 |
| 主会话 | 作者直接对话的那个 Agent，负责写任务书、派活、复审 |
| 子代理、孙代理 | Agent 派出去替它办事的另一个 Agent 叫子代理；子代理再派出去的叫孙代理 |
| 上下文 | AI 在一次对话里能同时看到的全部文字，有长度上限 |
| 压缩 | 对话太长时，工具把前面的内容自动缩写成摘要，细节会丢失 |
| token（计费） | 模型计算文字量和费用的单位，大约一个汉字算一两个 |
| 缓存 | 模型对读过的内容的短期存储，再次使用时更便宜；换模型后要重新读取 |
| 模型档位 | 按能力和价格把模型分成几级：旗舰（最强最贵）、默认、机械批改、只读检索 |
| 降档、升档 | 换用更便宜的模型叫降档，换用更强的模型叫升档 |
| 推理强度 | 让模型在回答前思考多少的一个调节项，越高越慢越贵 |
| 记忆 | Agent 写给以后的会话阅读的笔记文件 |
| AGENTS.md、CLAUDE.md | 放在项目里的“项目手册”，Agent 每次开工自动阅读。Codex 读前者，Claude Code 读后者 |
| 规范 | 写在项目手册里的规则的总称 |
| 硬性规则 | 任务书开头那几条违反一条就作废交付的规则 |
| `/goal` | Claude Code 的一个指令：给一个目标，让它一直做到条件满足或达到轮数上限 |
| `/loop` | Claude Code 的一个指令：每隔一段时间重复做一件事，适合等待和查看进度 |
| `/clear` | 清空当前对话内容，从头开始 |
| `/code-review` | Claude Code 的一个指令：让另一组 Agent 检查刚才的修改有没有毛病 |
| plan mode | Claude Code 的“只写计划、不动手”状态，要等人批准才开始做 |
| superpowers | 一个第三方做的 Claude Code 插件，里面是一组写好的工作方法（称为技能） |
| hook（钩子） | 挂在某个动作前后自动运行的小程序，例如在 Agent 执行命令之前先检查这条命令允不允许 |
| 放行表 | 一张“这些命令不用问我，直接执行”的清单 |
| DOM、无障碍树 | 程序内部对界面的文字描述，写着每个按钮叫什么、在什么状态 |

## 和代码管理有关

| 词 | 白话解释 |
|---|---|
| 仓库 | 存放一个项目全部代码和修改历史的地方 |
| 公开仓、私有仓 | 所有人都能看的仓库、只有自己人能看的仓库 |
| open-core | 核心部分开源、收费功能不公开的做法 |
| git | 记录代码每一次修改的工具，可以回看历史，也可以多人同时修改 |
| 提交（commit） | 把一批修改正式存进历史，相当于存档一次 |
| 提交号 | 每次提交的唯一编号 |
| 推送（push） | 把本机的提交上传到 GitHub 上的仓库 |
| 分支 | 从主线分出来的一条独立修改线，做完再合并回去 |
| 集成分支 | 所有新修改先汇合到的那条分支，阿布叫 dev |
| 发版分支 | 对外发布的版本所在的分支，阿布叫 main |
| 合并、合入 | 把一条分支上的修改并进另一条分支 |
| 快进 | 一种合并方式：发版分支原样跟上集成分支，不产生任何新的提交 |
| cherry-pick | 只挑一条分支上的某一个修改，复制到另一条分支 |
| 强制推送 | 用本机的历史覆盖 GitHub 上的历史，别人已经上传的修改会消失 |
| 用 git 回滚 | 用一条 git 命令把文件恢复成以前的样子，还没提交的修改会一起消失 |
| 回退 | 部署或升级出问题时换回旧版本 |
| worktree | 同一个仓库的另一个独立工作目录，几个 Agent 各用一个，互不干扰 |
| 检出 | 把某条分支的代码取到本机的一个目录里 |
| 工作区干净 | 没有任何还没提交的修改 |
| `.gitignore` | 一张“这些文件不要存进仓库”的清单 |
| /tmp | 电脑上的临时目录，重启后里面的文件可能被清空 |
| PR（合并请求） | 在 GitHub 上提出“请把我这条分支合并进去”的申请，别人可以在上面检查和评论 |
| Draft PR | 标成“草稿”的 PR，只给人看，不会被合并 |
| 叠放 PR | 一个 PR 建立在另一个还没合并的 PR 之上 |
| base 分支（目标分支） | PR 想要合并进去的那条分支 |
| 自动合并 | 给 PR 打开的一个开关：检查全部通过后自动合并，不用人点击 |
| 分支保护 | GitHub 上给重要分支加的锁，例如检查不通过就不能合并、不允许强制推送 |
| 必需检查 | 在分支保护里登记过的检查，它不通过，PR 就合并不了 |
| issue | GitHub 上的一条问题或待办记录 |
| label | 贴在 PR 或 issue 上的标签 |
| tag | 给某一次提交贴上的版本号标签，例如 v1.2.0 |
| 复审 | 由另一个人或另一个 Agent 检查修改 |

## 和检查、测试有关

| 词 | 白话解释 |
|---|---|
| 命令、脚本 | 在终端里输入的一行指令；把多行指令存成文件就是脚本 |
| 退出码 | 命令结束时报告的一个数字，0 代表成功，其他数字代表失败 |
| 管道 | 把一条命令的输出交给另一条命令处理；屏幕上看到的成功或失败变成后一条命令的 |
| lint | 自动检查代码写法是否符合约定的工具，类似文档里的拼写检查 |
| 类型检查 | 自动检查代码里数据种类有没有用错，例如把文字当成数字 |
| 构建（build） | 把源代码加工成可以运行的程序 |
| 测试 | 一段自动运行的程序，检查功能是否按预期工作 |
| 单元测试、集成测试 | 只检查一小块功能的测试；检查几块功能合在一起的测试 |
| 契约测试 | 检查两个部分之间约定好的数据格式有没有被某一方改掉的测试 |
| E2E（端到端测试） | 让程序像真人一样打开应用、点击按钮，检查整条流程的测试 |
| 冒烟 | 最简单的一次试运行，只确认程序能启动、主要功能能用 |
| 覆盖率 | 全部代码里被测试运行到的比例 |
| 阈值 | 一条及格线，低于它检查就失败 |
| 门禁 | 把 lint、类型检查、全部测试串成一条命令，通过了才算做完 |
| verify | 阿布里门禁命令的名字 |
| 红、绿 | 检查失败显示红色，通过显示绿色；“假红”指其实没有问题却显示失败，“假绿”指有问题却显示通过 |
| CI | 代码上传后，GitHub 上自动运行检查的机器 |
| workflow、job | CI 里的一套自动流程叫 workflow，流程里的每一项任务叫 job |
| 汇总检查 | CI 里专门确认“其他各项检查都通过了”的那一项 |
| pre-commit | 每次提交之前自动运行的检查 |
| `--no-verify` | 提交时附加的一个选项，作用是跳过提交前的检查 |
| mock（替身） | 测试时用来代替真实网络、真实时间的假部件 |
| 不稳定测试 | 同样的代码，这次通过、下次失败的测试 |
| 隔离区 | 暂时存放不稳定测试的地方，有修复期限 |
| 回归 | 以前正常的功能被新的修改弄出毛病 |
| 误报 | 检查或复审说有问题，核实后发现没有问题 |
| 降级（复审裁定） | 问题存在，但没有报告说的那么严重 |
| 对抗式审查 | 专门站在捣乱的用户和奇怪数据的角度找问题的检查 |
| 变异测试 | 故意把一段防护代码改错，看有没有测试能发现 |

## 和发版、部署有关

| 词 | 白话解释 |
|---|---|
| 发版、Release | 把一个新版本正式发给用户；Release 是 GitHub 上放安装包的页面 |
| RC | 候选版本，正式发布前先试一遍用的版本 |
| patch、minor、major | 版本号的三段：只修复问题、加了新功能、有不兼容的大改动 |
| 更新日志 | 每个版本修改了什么的说明文件 |
| 更新服务器 | 应用检查“有没有新版本”时访问的地址 |
| 预检 | 发版前自动核对版本号、更新日志等是否齐全的检查 |
| 依赖 | 项目用到的别人写好的代码包 |
| 锁文件 | 记录每个依赖确切版本的文件 |
| Dependabot | GitHub 自带的机器人，定期替你申请升级依赖 |
| 漏洞审计 | 自动查询依赖里有没有已知安全漏洞 |
| 部署 | 把服务端程序放到服务器上运行 |
| 镜像 | 把程序和它需要的环境打成的一个包，服务器拿到就能运行 |
| 健康检查 | 部署后自动访问一次，确认服务还在正常工作 |
| 密钥、`.env` | 访问各种服务用的密码；`.env` 是存放这些密码的文件，不能上传 |
| 登录 token | 登录后服务器发给你的通行凭据 |
| 设计变量 | 界面样式里统一定义的字号、颜色等取值，代码里常叫 design token |
| 遥测、埋点 | 应用把使用情况上报给开发者；埋点是上报的每一个记录点 |
| 主进程、界面进程 | 桌面应用里有权限读写文件的后台部分，和只负责显示界面的部分 |

## 模板仓库自己的词

| 词 | 白话解释 |
|---|---|
| 盘点 | 作者把阿布现有的全部规则和检查逐条清点了一遍，共 321 项；每条规则对应的盘点编号在[盘点对照表](盘点对照表.md)里 |
| 强度 L0–L3 | 一条规则被违反时拦不拦得住：L0 只是口头说过，L1 写进手册，L2 有检查但能绕过，L3 机器强制拦截 |
| 任务书（brief） | 动手之前写给 Agent 的文件，写清要做什么、怎样算做完；文件名以 `-brief.md` 结尾 |
| 竞品调研记录（reference） | 亲自打开竞品看过之后写下的“竞品怎么做、我们怎么做”；文件名以 `reference-` 开头 |
| 派活指令 | 粘贴给执行 Agent 的开工的一段话 |
| 交付说明 | Agent 做完后交给人的成果单，写清做了什么、证据在哪、哪些要人决定 |
| 晨报 | 夜间无人值守之后，早上交给人阅读的第一份文件 |
| 台账 | 按时间顺序一行一行记录的进度本 |
| 裁定（Ruling） | 执行过程中做出的一个决定，连同理由一起记录 |
| 批次、轨道 | 一次交给 Agent 的一组任务叫批次；批次里可以同时进行的每一条独立工作叫轨道 |
| 收工条件 | 写在任务书里、可以用命令检查的“全部做完”的标准 |
| 上限 | 最多运行多少轮或到几点必须停止 |
| 待拍板 | 交付说明里的一节，列出 Agent 停下来没有自己决定的产品问题 |
| 待确认 | 任务书顶部的一节，只记实现中发现需要、却不在功能清单里的界面元素 |
| 真机验收 | 人在真实的应用里亲手操作一遍 |

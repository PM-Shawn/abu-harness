# 阿布的研发 harness

看不懂的词查[常用词解释](00-全景/常用词解释.md)。

这是作者开发桌面 AI 助手“阿布”（开源仓库 [PM-Shawn/Abu-Cowork](https://github.com/PM-Shawn/Abu-Cowork)）时，用来管理 Claude Code 和 Codex 的整套规则、模板和脚本。有了它，Agent 可以在没人看着的时候连续开发一整晚，作者第二天早上按清单验收。

harness 原意是马具。放在这里，指套在 AI 身上的一整套规矩和检查：告诉它往哪走、哪里不能去、怎样算做完、做过的事记在哪、出了事怎样改规矩。

## 适合谁

主要读者是会用 Claude Code 的人：自己写代码的程序员，或者让 Agent 替自己操作的产品经理。

- 已经在用 Claude Code、Codex、Cursor 之类工具写代码，想让 Agent 独立做完更大的任务；
- 被 Agent“说修好了其实没修好”“改着改着把别的东西改坏了”“换个会话就忘了之前的决定”困扰过；
- 不写代码的读者靠三样东西读懂：[常用词解释](00-全景/常用词解释.md)、每个目录开头的真实故事、每条规则的“防的是什么”。规则文字可以直接复制使用。

## 怎样开始

不需要一次全部照搬。按下面的顺序，每一步都能单独起作用。

**自己写代码的读者**照 [INSTALL.md](INSTALL.md) 做，它写明每一步要复制哪些文件、放在哪里、运行哪些命令和装哪些依赖，步骤编号与下面相同。

**不写代码的读者**先读[一个真实的夜晚](00-全景/一个真实的夜晚.md)和[全景图](00-全景/全景图.md)，再按下面每一步，把引号里的话粘贴给 Claude Code（在你的项目目录里打开它，并让它能读到这套材料所在的目录），然后按“怎样确认”核对。

1. **写一份项目手册。** 项目根目录放一份 `AGENTS.md`（Claude Code 读 `CLAUDE.md`，可以只写一行 `@AGENTS.md` 导入），先从[边界](03-边界/README.md)和[判定](02-判定/README.md)里挑五到十条最痛的规则抄进去。
   粘贴：“把这个目录里的 01-方向/mechanisms/CLAUDE.md 复制到我的项目根目录，旁边新建 AGENTS.md，把 03-边界/README.md 里‘git 操作’一组的规则原文抄进去。”
   怎样确认：打开 `AGENTS.md` 能看到这些规则；新开一个会话问它“我们的项目手册里有哪几条规则”，它能复述出来。
2. **装一个拦截钩子。** 把[边界](03-边界/README.md#不用-git-回滚)里的 Claude Code hook 装上，拦下“一条命令把还没保存进版本库的修改全部清除”这类手册拦不住的操作。
   粘贴：“把这个目录里的 03-边界/mechanisms/claude-code-guard 按 INSTALL.md 第 2 步装到我的 Claude Code 里，装完运行它自带的测试，把结果给我看。”
   怎样确认：它报告 41 个用例全部 PASS、退出码 0；再让它“试着运行 git stash”，它应当说这条命令被钩子拒绝了。
3. **定一个“做完”的标准。** 用一条命令跑完 lint（自动检查代码写法）、类型检查和全部测试，只认它的退出码（命令结束时报告成功还是失败的一个数字，0 代表成功）。见[判定](02-判定/README.md#做完了只认门禁退出码)。
   粘贴：“按 INSTALL.md 第 3 步给这个项目装上门禁，装完运行 bash scripts/run-gate.sh verify，把最后一行给我看。”
   怎样确认：最后一行是 `REAL_EXIT=0`；让它故意写一个有错误的文件再提交，提交应当被拦下。
4. **让 CI 替你把关。** 把这条命令放进 CI（代码上传后 GitHub 上自动运行检查的机器），登记成分支保护的必需检查（没通过就不允许合并），检查失败的 PR（在 GitHub 上提出的合并申请）合并不了。见[判定](02-判定/README.md#ci-用汇总检查作为必需检查)。
   粘贴：“按 INSTALL.md 第 4 步装 CI 汇总检查；分支保护要我在 GitHub 网页上设置，告诉我进哪个页面、勾哪几项。”
   怎样确认：开一个 PR，页面上显示名为 `check` 的检查，没通过时合并按钮不可用。
5. **开始记录。** 用[记录](04-记录/README.md#记忆按四种类型分文件保存)里的记忆模板，让 Agent 在被你纠正时当场记下教训。
   粘贴：“读这个目录里的 04-记录/templates/memory，以后我纠正你的时候，当场按 feedback 示例的格式写一条记忆并更新索引。”
   怎样确认：故意纠正它一次，看记忆目录里多了一个 feedback 文件，索引里多了一行。
6. **试一个晚上。** 用[方向](01-方向/README.md#夜间任务书写清收工条件)里的任务书和派活指令模板，交代一件边界清楚的小事，第二天按交付说明验收。
   粘贴：“照这个目录里的 01-方向/templates/overnight-brief.md 替我写一份夜间任务书，功能是【一句话】，收工条件每条都要能用命令检查；写完把 dispatch-prompt.txt 填好给我。”
   怎样确认：早上打开交付说明，先读“待拍板”和“真机验收清单”两节，照清单在真实的应用里点一遍。

## 每条规则怎样读

每个目录先有一张“规则一览”表，然后每条规则一个小节，固定六栏：

| 栏 | 写什么 |
|---|---|
| 规则原文 | 可以直接复制进 `AGENTS.md` / `CLAUDE.md` 的写法 |
| 防的是什么 | Agent 会犯什么错、后果是什么 |
| 阿布里的来历 | 真实事故或出处；规范里没写来历的，如实写“规范里未写明来历” |
| 强度 | 这条规则被违反时拦不拦得住，用 L0–L3 表示；一条规则有几层时按层写，例如“规范 L1；CI L3” |
| 执行机制 | 对应的脚本、钩子、模板在哪里；没有的写“暂无，只靠 Agent 读规则” |
| 怎样用到你的项目 | 复制时要改什么 |

不写代码的读者只读前三栏。

“规则一览”表的“适用范围”有四种取值：

- **通用**：任何项目都能用；
- **来自阿布，已改写成通用版本**：阿布因为自己的框架或结构定下的规则，这里改写成了不依赖阿布的写法；
- **可选模块**：只在某种情况下需要，括号里写明是哪种情况；
- **个人风格**：作者个人对 Agent 工作方式的要求，放在各目录最后一节，读者按自己情况取舍。

## 强度等级

每条规则都标了强度（详细定义见[全景图](00-全景/全景图.md#四个强度等级)）：

- **L0** 只在对话里说过，没有写进任何文件；
- **L1** 只写在手册里；
- **L2** 有检查，但能绕过；
- **L3** 机器强制拦下。

这些强度都是如实标注的。阿布自己有 321 项规则和检查，一半左右停在 L1；另有一项“不生效”（一个写了 `if: false`、永远不运行的旧 workflow）。各目录末尾的“还没补上的缺口”写了具体是哪些地方。

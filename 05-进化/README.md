# 进化

看不懂的词查[常用词解释](../00-全景/常用词解释.md)。

Agent 不会自己从错误里学习：这个会话被纠正过的事，下一个会话照样会做错；门禁也会随时间松动。阿布里的真实例子：2026-06-30 隔离了第一批不稳定测试，期限四周，可检查期限用的“今天”被写成固定日期，时钟从没有往前走，超期两个月没有任何检查变红，直到 2026-09-02 才有人发现并删除。

进化这项制度要求每一次纠正和事故都变成文字，再变成规范，能交给机器的再变成检查，并让门禁只能变严、定期被重新审视。

## 规则详解

### 被纠正或出事故时当场写 feedback 记忆

**规则原文**

> 用户纠正你、或者出了事故时，当场写一条 feedback 记忆：发生了什么（带日期），**Why**（机制层面的原因），**How to apply**（以后遇到什么情况、具体怎么做）；同时在记忆索引里加一行。依据用户的原话写，不改写成自己的理解。

- **防的是什么**：同一个错误在新会话里重犯；用户要一遍遍重复同样的纠正。
- **阿布里的来历**：阿布有 16 条 feedback 记忆，例如：门禁命令接 `| tail` 把失败显示成成功；压缩后接着执行的会话沿用了过时的版本号（2026-09-16）；没查裁定记录就断言“这里设计有问题”（2026-09-14）；孙代理用 git 撤销改动（2026-09-25），当天就写成一条 feedback 记忆“派子代理时，禁令要写明‘你再派的子代理也必须遵守’”。
- **强度**：L1。写不写全靠 Agent 自觉。
- **执行机制**：[templates/incident-to-rule.md](templates/incident-to-rule.md) 第一步；feedback 记忆的文件格式见 [04-记录 的示例](../04-记录/templates/memory/feedback-example.md)。
- **怎样用到你的项目**：把“被纠正或出事故时当场写 feedback 记忆”写进 AGENTS.md；不用 Claude Code 时把记忆放在仓库里的固定目录。

### 事故之后把规则写进规范并注明来历

**规则原文**

> 同一类问题出现第二次，或者后果严重时，把教训写进 AGENTS.md / CLAUDE.md 对应的小节，并在标题或行尾写明来历（例如“2026-09-06 事故后定”）。写进规范后，在对应的 feedback 记忆里注明“已写进 AGENTS.md「小节名」”。能交给机器检查的，再补 hook、lint、测试或 CI 检查。

- **防的是什么**：教训只留在一台机器的记忆里，别的工具、别的机器以及别的人看不到；规范里的规则没有来历，后来的人不知道它防的是什么，改规则时容易把它删掉。
- **阿布里的来历**：2026-09-06 阿布出了一次叠放 PR 事故：子 PR 的 base 是没有分支保护的父特性分支，提前开的 auto-merge 把子 PR 立即合进了父分支，整串叠放 PR 都合错了位置。当天工作区 AGENTS.md 加了“叠放 PR 合并纪律（2026-09-06 事故后定）”一节。另一例：作者要求“先写用户故事再做技术方案”，先记成 feedback 记忆，2026-09-19 写进 AGENTS.md 的“开发前置流程”，记忆里注明了已写进规范。
- **强度**：L1。规范文件本身靠 Agent 读入，没有检查。
- **执行机制**：[templates/incident-to-rule.md](templates/incident-to-rule.md)。叠放 PR 规则的正文见 [03-边界](../03-边界/README.md#叠放-pr-不提前开自动合并)，工作区总规范见 [01-方向](../01-方向/README.md#规范只有一份来源)。
- **怎样用到你的项目**：规范文件里每条事故规则都带日期和一句来历；定期检查 feedback 记忆里有没有应该升级为规范的条目。

### 每两三周做一次对抗式审查

**规则原文**

> 每 2–3 周对全项目做一次从最基本的道理出发的对抗式审查，不等改动触发：用多个 Agent 并发审查架构、依赖关系、代码质量、文档与代码是否一致、技术债，站在“恶意用户 / 怪异数据”的角度找问题。每条发现先证伪再动；确认的问题记进 issue 或 TODO 并排期。顺带用来检验新模型的能力，并回看近两三周合入的功能。高风险领域的对抗清单在每次审查后补上新出现的攻击类别和对应测试。

- **防的是什么**：只审查改动，已有的代码里的问题永远没人看；文档与代码越差越远。
- **阿布里的来历**：规范里未写明来历。复审报告的误报很多：阿布一次复审的 17 条发现里 14 条是误报。对抗式审查产出更多，更要先证伪。
- **强度**：L1。没有定时任务。
- **执行机制**：[templates/periodic-adversarial-review.md](templates/periodic-adversarial-review.md)。先证伪再动的规则正文见 [02-判定](../02-判定/README.md#复审发现先证伪再动手)。
- **怎样用到你的项目**：在日历或定时任务里设好周期；审查报告里每条发现都要有“去向”一列。

### 用变异测试判断防御是否有效

**规则原文**

> 判断一条防御是否真的有效，靠变异测试：把防御代码改坏，看有没有测试变红。没有测试变红，说明这条防御没有被测到。新增对抗清单的一行时，顺手做一次。

- **防的是什么**：几千条测试全绿，给人“都测到了”的错觉；门禁对静默漏检、静默丢字段这类问题看不见。
- **阿布里的来历**：阿布浏览器自动化领域的两次教训：登录探测器静默漏检（修了三轮）、审批审计字段在白名单边界被静默丢弃，两次都是各层测试全绿、整条链路是断的。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。可以手工做（注释掉一行防御代码，运行相关测试），也可以用 Stryker 这类变异测试工具。
- **怎样用到你的项目**：在对抗清单或 PR 模板里加一项“已做变异验证：去掉防御后 【测试名】 变红”。

### 门禁脚本和 lint 规则也要有测试（可选）

适用于自己写了门禁脚本或自定义 lint 规则的项目。

**规则原文**

> 门禁脚本（覆盖率检查、测试清单、依赖审计检查、CI workflow 结构等）用 `node:test` 写测试，放进 `test:infra`，在 CI 里运行。自定义 lint 规则用 ESLint API 写测试，证明规则会报错、也不会误报。

- **防的是什么**：门禁脚本自己有 bug，一直显示通过；lint 规则的正则或 glob 写错，规则悄悄失效，lint 仍然是绿的。
- **阿布里的来历**：规范里未写明来历。一个相关的实例：阿布一次 CI 改动的复审发现，审计步骤后面接了 `| tee`，在默认 shell 下脚本的失败退出码被吞掉，这个 job 永远不会变红；修复时同时加了检查 workflow 结构的测试。
- **强度**：L2。`test:infra` 不在 `verify` 里，CI 的必需检查里有；lint 规则测试随全量测试运行。
- **执行机制**：[mechanisms/lint-ratchet/eslint-rules.test.ts](mechanisms/lint-ratchet/eslint-rules.test.ts)。`test:infra` 的写法与 [02-判定 的 verify-scripts.jsonc](../02-判定/mechanisms/verify-scripts.jsonc) 相同：`"test:infra": "node --test \"scripts/*.test.mjs\""`，每个门禁脚本旁边放一个同名的 `.test.mjs`，放进 `scripts/` 就会被运行。
- **怎样用到你的项目**：门禁脚本导出纯函数（例如本目录的 `npm-audit-check.mjs` 导出了清单解析和判定函数），测试直接调用这些函数。

### 渐进迁移用只增不删的名单

**规则原文**

> 新的代码规则不能一次让全部旧文件达标时，用一份迁移名单：lint 规则只对名单里的文件生效；某个目录或文件迁移完，就在同一个 PR 里把它加进名单；名单只增不删。全部迁移完后删掉名单，让规则对所有文件生效。

- **防的是什么**：迁移完的文件被后来的改动改回旧写法；迁移进度只能靠人记。
- **阿布里的来历**：阿布设计系统迁移时，ESLint 配置里写明“迁移完一个目录就追加一个 glob，永远不删”。
- **强度**：L2。可以用 disable 注释绕过；规则只对名单里的文件生效；“永远不删”没有检查。
- **执行机制**：[mechanisms/lint-ratchet/eslint.migration-list.mjs](mechanisms/lint-ratchet/eslint.migration-list.mjs)，规则自测见 [eslint-rules.test.ts](mechanisms/lint-ratchet/eslint-rules.test.ts)。名单内的文件原本受到的导入限制和测试文件规则，通过 `migrationConfigs` 的参数传进去合并，与另外两个 ESLint 片段合用的写法见 [INSTALL.md 第 3 步](../INSTALL.md#第-3-步-做完的标准)。
- **怎样用到你的项目**：把示例规则换成你要推行的新规则；在迁移任务书里写明“迁移完在同一个 PR 追加名单”。

### 连续修不好就升档

**规则原文**

> 出现下面任何一种情况，换用更强的模型档位（升档）：连续两次修不好；改动跨越进程或模块边界；涉及权限或用户数据；下一步不可逆。升档后把这一类任务记进“不再降档”清单，以后同类任务直接用强模型。

- **防的是什么**：便宜模型反复返工，总成本反而更高；同一类任务每次都先用便宜模型做砸一次。
- **阿布里的来历**：规范里未写明来历。阿布按“做错了有没有能自动判断对错的检查能发现”给任务分配模型，没有这种检查的任务不降档。
- **强度**：L1。
- **执行机制**：[templates/no-downgrade-list.md](templates/no-downgrade-list.md)。模型分档的规则见 [01-方向](../01-方向/README.md#按做错了谁能发现来选模型)。
- **怎样用到你的项目**：把“进程或模块边界”换成你项目里的具体边界（例如前端与后端、主进程与界面进程）；清单放在 AGENTS.md 模型分档一节下面。

### 依赖自动升级并只自动合并低风险升级

**规则原文**

> 用 Dependabot（GitHub 自带的机器人，定期替你申请升级依赖）每月一次按 patch / minor 分组开升级 PR，目标是集成分支。patch 升级和 GitHub Actions 版本升级自动开启 auto-merge，等全部必需检查通过后合并；minor 和 major 升级留给人审。只接受发往集成分支的 Dependabot PR 自动合并。已冻结、不再发布的目录不扫描。

- **防的是什么**：依赖越来越旧，某天要一次升级几十个包；安全更新 PR 绕过集成分支直接进主分支；已冻结目录的升级 PR 没人处理，成为噪音。
- **阿布里的来历**：workflow 注释写明两点：Dependabot 的安全更新 PR 可能指向默认分支，不能绕过唯一的集成线，所以同时限定目标分支；已冻结的旧桌面框架目录的依赖升级不会发到任何地方，只制造 PR 噪音，所以停止扫描。
- **强度**：自动合并 L3；升级 PR L2。自动合并前要等分支保护登记的必需检查全部通过；Dependabot 配置本身只开 PR。
- **执行机制**：[mechanisms/dependabot/dependabot.yml](mechanisms/dependabot/dependabot.yml)、[mechanisms/dependabot/dependabot-auto-merge.yml](mechanisms/dependabot/dependabot-auto-merge.yml)。
- **怎样用到你的项目**：先确认集成分支有分支保护并登记了必需检查、仓库打开了“Allow auto-merge”。集成分支没有分支保护时，auto-merge 会立即合并，不要启用这个 workflow。

### 漏洞允许清单带到期日（可选）

适用于 npm 项目，且有上游暂时没有修复版本的漏洞。

**规则原文**

> 生产依赖里的 high / critical 漏洞必须被一条未过期的允许条目覆盖，否则审计失败。每条允许条目写 GHSA 编号（GitHub 给每个已知漏洞的编号）、包名、理由（包括查证过程）、到期日；到期后审计失败，逼着重新审一遍。已经不再命中的条目提示删除。

- **防的是什么**：npm audit 无法接受上游没有修复的漏洞，审计永远是红的，大家不再看它，它也就没人再看；接受过的漏洞永远没人再审。
- **阿布里的来历**：检查脚本注释写明了上面的原因。阿布的允许清单里有两条上游没有修复版本的解析器漏洞，理由写明了只经哪个包间接引入、构建产物从不加载它，到期日 2026-12-31。
- **强度**：L2。本地没有 npm 脚本、不在 `verify` 里；CI 的 audit job 会变红，但不是必需检查，不阻止合并。
- **执行机制**：[mechanisms/audit/npm-audit-check.mjs](mechanisms/audit/npm-audit-check.mjs)、[mechanisms/audit/npm-audit-allowlist.json](mechanisms/audit/npm-audit-allowlist.json)、[mechanisms/audit/ci-audit.yml](mechanisms/audit/ci-audit.yml)。
- **怎样用到你的项目**：复制三个文件，清空示例条目；把 audit job 登记为必需检查，才能真正拦住合并。

### 全自动部署之前先有自动回退

**规则原文**

> 先做到“部署前记下旧版本，健康检查失败就自动换回旧版本”，再开启“推送代码后自动部署”。

- **防的是什么**：一个坏版本被自动推上线，健康检查失败后新版本仍在运行，只能等人手动恢复。
- **阿布里的来历**：2026-08-26 阿布运营后台的部署流程第一次实际运行成功时定下这条；现在的部署脚本会记下旧镜像 ID，健康检查失败时只提示人工回退。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：部署脚本先记下当前运行的版本，健康检查失败时自动切回并以非零退出码结束；这一步做完并演练过一次，再打开自动部署。

## 还没补上的缺口

| 问题 | 后果 | 打算补的机制 |
|---|---|---|
| 调低覆盖率阈值本身没有任何检查；改动行覆盖率只在一个仓库的 PR CI 里有，其他仓库没有 | 阈值被调低时没有检查变红；其他仓库新增的代码可以没有测试 | CI 必需检查：阈值不得低于集成分支上的阈值；其他仓库加改动行覆盖率 |
| 隔离期限检查在本地用固定日期；一个仓库完全没有 CI 注入当天日期 | 本地 verify 永远不会因隔离超期变红；没有 CI 注入的仓库，隔离超期无人发现 | 所有运行门禁的地方都注入当天日期 |
| 双周对抗式审查没有定时任务 | 已有的问题没有人定期检查 | 定时任务 |
| 部署的健康检查失败后没有自动回退，新版本仍在运行 | 恢复只能靠人 | 部署脚本记录旧版本，健康检查失败时自动切回 |
| 依赖漏洞审计、Windows 单测等检查只做参考，红了也能合并 | 依赖漏洞红了照样合并 | 逐项评估后加入必需检查 |
| Dependabot 只在一个仓库启用 | 其他仓库的依赖只能靠人想起来升级 | 各仓库加 Dependabot 配置 |

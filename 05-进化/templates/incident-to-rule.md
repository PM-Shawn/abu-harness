# 从一次纠正或事故到一条规则

<!--
用法：用户纠正 Agent、或者出了事故时，按下面三步处理。
第一步当场做；第二步在同一类问题出现第二次、或者后果严重时做；第三步能做就做。
【……】包住的文字是占位，换成你自己的内容；示例是虚构的。
-->

## 第一步：当场写 feedback 记忆

文件：`memory/feedback-【主题】.md`（格式见 `04-记录/templates/memory/feedback-example.md`）

必须写清：

- 发生了什么（日期、在做什么、错在哪一步）；
- **Why**：为什么会错（机制层面的原因，例如“禁令只写给了直接子代理，它再分派时只转述任务、不转述禁令”）；
- **How to apply**：以后遇到什么情况、具体怎么做。

同时在 `MEMORY.md` 加一行“是什么 + 什么时候翻”。

## 第二步：把教训写进项目手册，并注明来历

在 AGENTS.md / CLAUDE.md 对应的小节加一条规则，标题或行尾写明来历，例如：

```markdown
## 叠放 PR 合并纪律（【YYYY-MM-DD】事故后定）

- 叠放 PR（base 是功能分支）不提前开 auto-merge：base 没有分支保护时，auto-merge 会立即合并。
  正确顺序：父 PR 合入集成分支 → 改子 PR 的 base → 把集成分支合进子分支 → 本机门禁 → push → 再开 auto-merge。
```

写进手册后，回到第一步的 feedback 记忆，在 description 或正文里写一句“已写进 AGENTS.md「【小节名】」”，
避免两处各写一份、以后改了一处忘了另一处。

## 第三步：能交给机器检查的，补一个机制

| 规则 | 能不能交给机器 | 机制 |
|---|---|---|
| 【规则一句话】 | 能 / 不能 | 【hook / lint / 测试 / CI 必需检查 / 暂时没有】 |

补了机制之后，在手册里写明“由【机制】检查”；没补的写进缺口清单，写明问题、后果、打算补的机制。

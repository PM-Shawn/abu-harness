# 记录

看不懂的词查[常用词解释](../00-全景/常用词解释.md)。

Agent 每个会话都从零开始：昨天查清的事实、用户做过的裁定、夜里做到哪一步，它都不记得。记录这项制度要求 Agent 把这些写成以后能查的文字、台账、证据和提交信息。阿布 2026-09-14 晚上两个 Codex 会话无人值守执行个人账号批次，作者早上读交付说明里的“待拍板”和“真机验收清单”两节、看截图、手动走一遍浏览器跳回桌面端，就完成了验收。

反过来，记录写错也会误导后来的会话：阿布一份记忆写着“第 1 步在做”，同一批次的台账却写着“第 1 步没有开始”，按记忆接着执行的会话会读错进度。

## 规则详解

### 记忆按四种类型分文件保存

**规则原文**

> 跨会话要记住的事写成记忆文件，一件事一个文件，分四种类型：`user`（用户是谁、有什么习惯）、`feedback`（用户的纠正和事故教训）、`project`（某项工作的状态、裁定、坑、下一步）、`reference`（竞品调研结论、外部资料、工程上的坑）。文件开头用 frontmatter 写 `name`、`description`、`type`；`feedback` 和 `project` 的正文末尾写 **Why**（为什么）和 **How to apply**（以后遇到什么情况、怎么做）。`project` 记忆的状态带日期，每批结束、出现裁定、状态变化时更新；更新时改掉过时的旧状态，不在文末追加一段互相矛盾的新状态。记忆里提到的文件、函数、开关、版本号只作线索，用之前先核实。

- **防的是什么**：新会话重新调查已经查清的事、把已经裁定的做法当成缺陷再提一遍、重复踩同一个坑。
- **阿布里的来历**：阿布的 Claude Code 记忆目录有 158 个记忆文件（feedback 16、project 76、reference 63、user 2、归档 1）。反面例子见本目录开头：一份 project 记忆追加新状态时没改掉旧状态，与台账和实际文件都对不上。另一份记忆同一文件里既写“PR 已开 auto-merge”又写“还没推送”。
- **强度**：L1。Claude Code 会把记忆索引自动放进上下文，但写不写、写得对不对没有任何检查。
- **执行机制**：四种类型各一个示例：[user](templates/memory/user-example.md)、[feedback](templates/memory/feedback-example.md)、[project](templates/memory/project-example.md)、[reference](templates/memory/reference-example.md)。
- **怎样用到你的项目**：Claude Code 的记忆目录在 `~/.claude/projects/【项目路径】/memory/`；其他工具（例如 Codex）读不到这个目录，需要把记忆放进仓库里的某个目录，并在 AGENTS.md 里写明开工前要读。阿布的记忆文件还带 `modified` 等字段，可按需要加。

`user` 与 `reference` 记忆的规则正文在 [01-方向](../01-方向/README.md)（“记下用户是谁”“竞品调研亲自去看”），`feedback` 记忆的规则正文在 [05-进化](../05-进化/README.md)。

### 记忆索引一条一行

**规则原文**

> 记忆目录里的 `MEMORY.md` 是索引：一条记忆一行，只写“是什么 + 什么时候翻”，按“反馈 / 工作方式”“用户”“项目”“参考”分区。新增、删除、改名记忆文件时同时改索引。链接只指向真实存在的文件名。

- **防的是什么**：索引会被自动放进每个会话的上下文，写长了每一轮都要付出 token（模型计算文字量和费用的单位）；写漏了，Agent 不知道有这条记忆，照样重犯。
- **阿布里的来历**：阿布的索引 158 行、136 条。盘点时发现 24 个 project 文件不在索引里（抽查的 4 个都在归档里），记忆正文里有 7 个链接指向不存在的文件名。
- **强度**：L1。内容对不对没有检查。
- **执行机制**：[templates/memory/MEMORY.md](templates/memory/MEMORY.md)。
- **怎样用到你的项目**：直接复制索引模板，分区名按项目调整；把“新增记忆时同时改索引”写进 AGENTS.md。

### 结项的记忆移进归档

**规则原文**

> 某项工作全部合入或关闭后，把它在索引里的那一行移到 `archive-closed-items.md`，行尾写一句结论；记忆文件本身保留。

- **防的是什么**：索引越来越长，已经结束的旧批次挤占上下文，还会让 Agent 以为旧工作仍在进行。
- **阿布里的来历**：2026-09-16 起，阿布把已结项的条目从索引移到归档，用来控制索引长度。
- **强度**：L1。
- **执行机制**：[templates/memory/archive-closed-items.md](templates/memory/archive-closed-items.md)。
- **怎样用到你的项目**：复制归档模板，在索引末尾加一行指向它。

### 交付说明必须有固定小节

**规则原文**

> 执行方完成一条轨道就更新一次交付说明，交给验收方。交付说明必须包含 11 个小节：轨道、分支、PR 与提交；实际使用的模型；门禁与覆盖率（真实退出码、覆盖率数字、日志位置）；独立复审；真实运行证据；截图清单；待拍板（所有停下来没有自己决定的产品问题，一条一句）；真机验收清单（验收人照着操作的步骤、期望结果、失败时看哪个日志）；与任务书不同之处及理由；限制与后续 TODO；最终检查点。所有数字来自真实运行的输出，中途失败过的写明失败记录。任务书的收工条件里检查这些小节是否齐全。

- **防的是什么**：Agent 自述“做完了”而人看不到证据；该人拍板的问题被 Agent 自己决定了；自动化做不到的验收步骤没人知道要做。
- **阿布里的来历**：阿布的 `docs/` 里约 26 份交付说明。2026-09-14 批次 2 的任务书规定了交付说明的必需小节，收工条件要求“必需小节齐全”；交付说明里保留了失败记录（一条轨道早期 verify 退出码为 0 但覆盖率低于阈值，不签收），真机验收清单写了 7 步。
- **强度**：L2。任务书的收工条件要求小节齐全，由执行方自查，没有脚本检查。
- **执行机制**：[templates/delivery.md](templates/delivery.md)，小节标题与 [01-方向 的 overnight-brief.md](../01-方向/templates/overnight-brief.md) 第 5 节一一对应。“真机验收清单”一节与 [02-判定 的 acceptance-checklist.md](../02-判定/templates/acceptance-checklist.md) 是同一种清单：前者写在交付说明里，由执行 Agent 填；后者是一个功能或一个 PR 单独成文件的清单，验收的人照着勾。截图、日志放哪里的规则见 [02-判定](../02-判定/README.md#行为类改动在真机上走一遍)。
- **怎样用到你的项目**：复制模板，在任务书里写“交付说明必须含下列小节”，并把“小节齐全”写进机器可验的收工条件。

### 交付里写明实际使用的模型

**规则原文**

> 委派子代理时显式指定模型（Codex 同时指定 `reasoning_effort`），不依赖默认继承；交付说明里写明实际用的模型组合。Codex 不用 `opus` / `sonnet` / `haiku` 这类别名。

- **防的是什么**：没指定模型时子代理继承主会话的模型，成本失控或能力不够；事后出了问题查不出是哪个模型做的。
- **阿布里的来历**：规范里未写明来历。实际交付说明里写了“实现 `gpt-5.6-sol + high`，安全复审 `gpt-6-astra + xhigh`”。
- **强度**：L1。
- **执行机制**：[templates/delivery.md](templates/delivery.md) 的“实际使用的模型”一节。
- **怎样用到你的项目**：把模型名换成你的工具支持的名称；模型分档的规则见 [01-方向](../01-方向/README.md#按做错了谁能发现来选模型)。

### 夜间执行日志与晨报

**规则原文**

> 无人值守执行时，执行 Agent 维护一份夜间执行日志：原样抄写用户睡前的话、写明上界（做完即停 / 最多几轮 / 最晚几点）、交付承诺（做什么、不做什么）、阶段状态表、带时刻的决策日志。第二天早上交一份晨报：最前面写必须让人知道的事，然后是今晚新交付、门禁证据、请人真机验收的步骤、已知边界、提交清单（写明是否已推送）。

- **防的是什么**：人醒来后不知道一晚上发生了什么，也不知道哪些要他验收、哪些要他拍板；Agent 在工具不可用时悄悄换了做法，人不知道。
- **阿布里的来历**：2026-09-01 的三份夜间记录：一份带时刻的决策日志；一份开头是“先说三件必须让你知道的事”（其中一件是本会话里 `/goal` 和 superpowers 技能都不存在，改用等价的做法）；一份五段式晨报，提交清单写“14 个，未 push”。
- **强度**：L1。
- **执行机制**：[templates/overnight-run-log.md](templates/overnight-run-log.md)、[templates/morning-report.md](templates/morning-report.md)。
- **怎样用到你的项目**：在夜间任务书里写明日志和晨报的文件路径，把“晨报存在”写进收工条件。

### 实现中遇到清单外的界面元素记进待确认

**规则原文**

> 实现中发现需要功能清单之外的界面元素时，不自己加，记进任务书顶部的“待确认”一节，写明对应哪个用户故事、为什么需要，然后跳过这一项，继续做不依赖它的部分。

- **防的是什么**：无人值守时 Agent 自作主张加入口、加开关，界面上出现用户不需要的东西。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。“待确认”放在任务书顶部，只记界面元素；“待拍板”放在交付说明，记所有停下来没有自己决定的产品问题。
- **怎样用到你的项目**：在任务书模板顶部留一个“待确认”小节，把“待确认已列全（可以为空）”写进自主循环的完成条件。

### 零散问题攒进问题队列

**规则原文**

> 走查、验收或诊断之后发现的零散问题，写进一份问题队列文件，按顺序开发。每条带 `file:line` 证据、业内对照、改法和门禁；执行后在文末追加执行记录。

- **防的是什么**：零散问题只留在对话里，过几天就找不到；没有证据的问题被当作事实去改。
- **阿布里的来历**：阿布有问题队列、修复队列、PR 队列三类文件，末尾有“执行记录（日期 夜）”。
- **强度**：L1。
- **执行机制**：[templates/issue-queue.md](templates/issue-queue.md)。
- **怎样用到你的项目**：也可以直接用 GitHub issue；关键是每条都带证据和门禁。

### 技术债记进 issue 并排期

**规则原文**

> 审查确认的技术债记进对应仓库的 issue 或 TODO 并排期，不许只留在审查报告里。

- **防的是什么**：审查报告写完就没人再看，确认过的问题永远不修。
- **阿布里的来历**：规范里未写明来历。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。定期审查的模板见 [05-进化](../05-进化/templates/periodic-adversarial-review.md)。
- **怎样用到你的项目**：在审查模板里给每条发现留一列“去向（issue 号）”。

### 提交信息用 Conventional Commits

**规则原文**

> 提交信息用 Conventional Commits 前缀（`feat:`、`fix:`、`refactor:`、`chore:`、`docs:`、`test:`）；每个有意义的变更单独提交。用 commit-msg 钩子和 CI 检查；不许换工具或跳过钩子绕过。

- **防的是什么**：提交历史看不出每次改了什么类型的东西，发版时整理更新日志、定位问题都困难。
- **阿布里的来历**：规范里未写明来历。企业版后台仓还要求提交标题和正文只用 ASCII，并写明“禁止通过换工具或跳过 hook 绕过规则”。
- **强度**：客户端 L1；企业版后台 L2。客户端只有规范，没有钩子；企业版后台的 commit-msg 钩子运行 commitlint、CI 检查 PR 里的每个提交，但可以 `--no-verify`，仓库也没有分支保护。
- **执行机制**：[mechanisms/commitlint.config.mjs](mechanisms/commitlint.config.mjs)、[mechanisms/commit-msg](mechanisms/commit-msg)（husky 钩子）、[mechanisms/commit-message-policy.yml](mechanisms/commit-message-policy.yml)（CI）。
- **怎样用到你的项目**：安装 `@commitlint/cli`、`@commitlint/config-conventional`、husky，复制三个文件（放在哪里、怎样确认钩子生效见 [INSTALL.md 第 5 步](../INSTALL.md#第-5-步-记录)）；团队用中文写提交信息时删掉 ASCII 规则；要让 CI 检查拦住合并，把它登记为分支保护的必需检查。

### 测试清单由脚本生成

**规则原文**

> 文档里各层测试的数量表由脚本从文件树统计生成，不手改。`test:inventory:check` 放进 verify 和 CI，文档过期就失败。

- **防的是什么**：文档里手写的测试数字很快过时，而 Agent 会把文档当作事实来读。
- **阿布里的来历**：脚本注释写明原因：手写的数字（例如“2400+ 个测试”“45 个文件”）会过时，AI Agent 把文档当作事实。盘点里另有多处文档描述与实际门禁不符的情况（例如文档写 5 个 spec，清单实际是 8 个）。
- **强度**：客户端 CI L3；本地 L2。客户端的 CI 必需检查 `check` 里运行 `test:inventory:check`；本地和企业版后台在 `verify:full` 里，可以不运行。
- **执行机制**：[mechanisms/test-inventory.mjs](mechanisms/test-inventory.mjs)。
- **怎样用到你的项目**：按文件中的注释改文档路径和分层规则，在文档里加一对标记，运行一次 `--write`，把 `--check` 放进门禁。

### 对抗清单只引用真实存在的测试

**规则原文**

> 高风险领域维护一张对抗清单：每行是一类攻击、期望行为、防住它的测试（`文件:测试名`）。没有对应测试的行不许写“已覆盖”；新增一类攻击面必须同时加一行和测试；引用的测试名必须真实存在，改测试名时同步改清单。

- **防的是什么**：清单写着“已覆盖”，实际测试早被改名或删除；各层单元测试全绿，整条链路却是断的。
- **阿布里的来历**：阿布浏览器自动化领域有过两次“各层单测全绿、整条链路是断的”：一次是登录探测静默漏检，一次是审批审计字段在白名单边界被静默丢弃。
- **强度**：L1。自检脚本只写在文档里，没有进 CI。
- **执行机制**：[mechanisms/check-checklist-refs.mjs](mechanisms/check-checklist-refs.mjs)（从文档里的自检命令整理而来：文档用 Markdown 解析库读取，测试名用 TypeScript 编译器从测试文件里取出，找不到的引用以退出码 1 结束）。
- **怎样用到你的项目**：清单里引用测试时统一写成反引号包起来的 `文件:测试名`，测试名与 `it` / `test` / `describe` 的名字完全相同；把脚本放进 `scripts/`，加一条 `check:checklist-refs` 脚本，放进 CI。

### 多语言更新日志一种语言一个文件

**规则原文**

> 更新日志按语言分文件（例如 `CHANGELOG.md` 全英文、`CHANGELOG.zh-CN.md` 全中文），每次发版每个文件都写本版本，同版本号、同结构，不混写。发版预检检查每个文件都有本版本且语言正确，不对就整个发版失败。

- **防的是什么**：更新弹窗给中文用户显示英文、给英文用户显示中文；漏写某种语言。
- **阿布里的来历**：规范里未写明来历。阿布的客户端按界面语言挑选对应文件里该版本的内容，显示在更新弹窗里。
- **强度**：L3。发版 workflow 的 preflight job 运行预检，失败则后续构建和发布都不运行。
- **执行机制**：发版预检脚本见 [02-判定](../02-判定/README.md#发版预检)。
- **怎样用到你的项目**：只有一种语言的项目不需要这条；多语言项目在预检脚本里检查每个文件里本版本的小节和字符集。

### Release notes 分三档写

**规则原文**

> Release notes 按 patch / minor / major 三档模板写。标题带一句话副标题；每条写用户能看到的变化和“为什么”；有数字给数字；patch 标题不加 emoji；末尾附 Full Changelog 链接；major 写迁移说明和回退办法。

- **防的是什么**：空的 Release（只写“See the assets below”），用户无法判断要不要升级。
- **阿布里的来历**：阿布 v0.13.5 的 Release 只写了“See the assets below”，被写进规范当反例。
- **强度**：L1。
- **执行机制**：[templates/release-notes.md](templates/release-notes.md)。
- **怎样用到你的项目**：把模板里的仓库名换成你的，放进发版文档。

### 敏感操作写审计日志

**规则原文**

> 登录、授权、License 变更、删除、权限或角色变更必须写审计日志。

- **防的是什么**：出了安全问题查不到是谁、什么时候做了什么。
- **阿布里的来历**：规范里未写明来历（企业版后台的规范）。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：列出你的项目里哪些操作算敏感操作，写进 AGENTS.md；可以在接口层加测试，检查这些接口调用后审计表多了一行。

### 构建产物带源提交号

**规则原文**

> 构建的镜像或安装包带上源代码的提交号（例如 Docker 镜像的 `org.opencontainers.image.revision` label），部署前用它核对“要部署的版本是不是线上版本的后代”。

- **防的是什么**：部署了一个比线上更旧、或者来自另一条分支的版本，却没人发现。
- **阿布里的来历**：2026-08-25 阿布运营后台部署时，没有核对线上实际运行的版本，一批从来没有上过线的提交跟着上去了，Web 界面全部报 500 错误约一小时。现在运营后台的镜像构建会打上提交号 label（workflow 注释里引用了这次事故），部署脚本读取线上镜像的 label 做核对。
- **强度**：L2。构建会打 label，但构建本身不运行测试；部署脚本可以不用。
- **执行机制**：暂无独立文件。GitHub Actions 里用 `docker/build-push-action` 时，在 `labels` 里加一行 `org.opencontainers.image.revision=${{ github.sha }}`；部署脚本用 `docker inspect` 读取线上容器的这个 label，再用 `git merge-base --is-ancestor 【线上提交】 【要部署的提交】` 核对。
- **怎样用到你的项目**：按上面的写法加 label 和核对步骤；核对失败就停止部署。部署核对本身的规则见 [02-判定](../02-判定/README.md#服务端部署前后的核对可选)。

### 跨仓共享的测试样本只有一个来源

**规则原文**

> 多个仓库共用同一组接口测试样本时，指定一份为规范副本，其他仓库的副本与它逐字节比较。修改时先改规范副本，再复制到各仓；检查脚本只检查、不自动复制。

- **防的是什么**：两个仓库各自改了自己的样本，接口两端的测试都是绿的，合在一起却对不上。
- **阿布里的来历**：规范里未写明来历。阿布的做法是各仓自带一份副本，原因是 CI 独立检出各仓，读不到共同的上级目录。
- **强度**：L2。检查放在 `verify:full` 里，本地可以不运行。
- **执行机制**：暂无独立文件。写一个脚本逐个比较两边文件的 sha256，任何一个不同或缺失就以非零退出码结束，放进 verify。
- **怎样用到你的项目**：只有一个仓库时不需要这条。找不到规范副本时要失败，不要打印警告后通过。

### 规范分在多个仓时写同步手册

**规则原文**

> 规范文件分在多个仓库时，写一份新机器同步手册：每个仓库在哪、规范在哪个分支、首次怎么拉取、日常怎么更新、在任意机器上改了规范怎么推回去。

- **防的是什么**：换一台机器后读到的是旧规范，或者只更新了其中一个仓库的规范。
- **阿布里的来历**：规范里未写明来历。阿布的规范分在工作区目录和两个子仓里；同步手册没有提到记忆目录，记忆只在一台机器上（见文末缺口）。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则（同步手册由人照着操作）。
- **怎样用到你的项目**：只有一个仓库时不需要；多个仓库时把记忆和台账的同步方式也写进手册。

### 逐任务进度台账（可选）

适用于使用 superpowers 插件 subagent-driven-development（SDD）流程的项目：主会话把任务逐个分派给子代理实现、再分派复审。不用 superpowers 插件的读者可以跳过。

**规则原文**

> 按计划逐任务执行时，主会话在 `progress.md` 台账里每做一个动作就在末尾追加一行：开头写计划、规格、worktree、起始提交、模型；然后是开工前的依赖检查表；之后每行一条任务状态（派出 / 已实现 / 复审中 / 第 x 轮修复 / 完成，附提交范围），裁定写成 `Ruling`，留到以后的小问题写成 `minor (deferred)`；结束时写收尾段。只在末尾追加，不在中间插入早期条目。新会话接着执行前先读完整份台账。批次结束时把台账复制到 `docs/` 长期保存。

- **防的是什么**：会话中断或上下文压缩后，不知道哪个任务做到哪一轮、哪些问题被推迟了；早期条目插在后面会让接着执行的会话读错进度。
- **阿布里的来历**：阿布工作区目录有 9 份、公开仓 2 份、worktree 里 2 份这种台账，14 份归档在 `docs/superpowers/ledgers/`。一份台账在“PR 已开”之后又出现了几个任务的早期条目，按行序阅读会读错进度。
- **强度**：台账 L2；归档 L1。复审子代理逐任务核查台账，但台账格式没有检查。
- **执行机制**：[templates/sdd-progress.md](templates/sdd-progress.md)。
- **怎样用到你的项目**：不用 superpowers 插件时也可以照这个格式手写台账；台账工作目录常被 `.gitignore` 忽略，要长期保存就复制进 `docs/`。

### 裁定写进台账并写明做错的代价

**规则原文**

> 执行中做出的每个决定（计划与实际不符时怎么办、用户当场的指示、子代理的修正是否接受）写成一条编号递增的 Ruling，并写明“做错的代价”。用户当场指定模型时（例如“这一批全程用某个模型”），这一批次的实现、复审、终审一律用这个模型，并记一条 Ruling。

- **防的是什么**：事后看不出为什么这样做；“做错的代价”写出来以后，代价大的决定会被多看一眼，代价小的可以放心往前走。
- **阿布里的来历**：阿布一份测试基建台账里有 R1–R27 共 27 条裁定，例如“用户 2026-09-02 指示全程用同一个模型，取代之前的分档裁定；做错的代价：token 花费更高，没有正确性风险”。
- **强度**：L1。规范要求“在台账记一条 Ruling”，没写台账在哪；Codex 侧没有这种台账。
- **执行机制**：[templates/sdd-progress.md](templates/sdd-progress.md) 里的 Ruling 写法。
- **怎样用到你的项目**：在 AGENTS.md 里写明裁定记在哪个文件；不用逐任务台账时可以记在交付说明或 project 记忆的“裁定”一段。

## 阿布专属规则示例

| 规则 | 为什么阿布需要它 |
|---|---|
| 旧桌面框架的冒烟 workflow 固定不运行（`if: false`），文件保留作迁移历史证据 | 阿布从 Tauri 迁移到 Electron，Electron 是唯一验收目标，旧文件只证明迁移前的状态 |

## 还没补上的缺口

| 问题 | 后果 | 打算补的机制 |
|---|---|---|
| 裁定记在台账里，台账目录被 `.gitignore` 忽略；记忆在用户主目录，不进 git；另一个 Agent 工具（Codex）的记忆目录是空的，也读不到 Claude 的记忆 | 换机器或换工具执行时看不到裁定和坑，会重复犯错 | 固定裁定的存放位置并进 git；把记忆或其中的裁定同步进仓库 |
| 记忆与实际不一致：状态追加后旧状态没改；记忆里写的模型分档与现行规范不同 | 接着执行的会话按记忆行事，读错进度和模型 | 删除过时内容；追加状态时要求改写状态段 |
| 记忆索引漏条目、正文链接指向不存在的文件、type 写错；台账在后面插入早期条目 | 链接失效，按行序阅读读错进度 | 脚本检查记忆链接与 type；台账只追加在末尾 |
| 任务书和交付说明把日志、证据放在 `/tmp` | 重启后证据丢失，交付说明里的链接失效 | 任务书模板改用仓库内证据目录；hook 拦截 `/tmp` 写入 |
| 提交信息规范只在一个仓库有钩子和 CI 检查，其他仓库只有文字要求 | 各仓提交信息格式不一致 | 各仓加 commit-msg 钩子和 CI 检查 |
| 发版后核对、部署记录、恢复演练只写在文档里，部署脚本不输出部署记录 | 更新源出问题要等用户发现；部署出事时找不到版本清单，不能证明可以回退 | 发版后自动核对各更新源的脚本；部署脚本输出部署记录；恢复演练脚本 |
| 对抗清单的引用自检只写在文档里，没有进 CI | 测试改名或删除后清单仍写“已覆盖” | 把自检脚本放进 CI |
| 文档对门禁的描述与实际不符，文档引用了不存在的文件 | Agent 把文档当事实，按错误的门禁情况行事 | 像测试清单一样由脚本生成门禁说明；链接检查脚本 |

## 作者的个人习惯（可选）

下面这条是作者对 Agent 输出方式的个人要求，读者按自己的情况取舍。

### 只写最终状态

**规则原文**

> 所有输出（回答、文档、注释、提交信息）只写最终状态。发现错误后直接改成正确的内容，不保留“之前 A 是错的，现在改成 B”之类的痕迹，也不解释为什么不用 A。

- **防的是什么**：文档里堆满修改过程，读者分不清哪句是现行规则；Agent 被指出错误后把错误原因反复写进文档和注释。
- **阿布里的来历**：规范里未写明来历。记忆里状态前后矛盾的问题（见上文缺口）就是违反这一条的结果。
- **强度**：L1。
- **执行机制**：暂无，只靠 Agent 读规则。
- **怎样用到你的项目**：需要保留修改历史的文档（例如更新日志、台账）不适用这条。
